# 오류 재발 방지를 위한 에이전트 학습 시스템 설계 — 선행 사례 조사

**최초 작성**: 2026-08-02
**최종 수정**: 2026-08-02
**대상 프로젝트**: grid fin (신규 개인용 개발 하네스)
**조사 도구**: Exa `/search` (auto), Firecrawl `/v1/scrape`

## 0. 조사 질문

grid fin 하네스에서 **스펙 설계 / 구현 계획 작성 / 구현** 각 단계의 오류를 검출·구조화하고, 회고 단계에서 하네스를 자체 강화해 같은 오류가 반복되지 않게 하려 한다. 이때 세 가지 난점이 있다.

1. 오류를 **어떤 스키마로** 구조화해야 재사용 가능한가
2. 축적된 지식을 **언제 어떻게 꺼내 써야** 예방이 되는가 (사후 대응이 아니라)
3. 학습이 쌓일수록 하네스가 비대해지고, 배운 것이 **하네스 원본에 반영되지 않고 프로젝트에만 남는** 문제를 어떻게 푸는가

본 문서는 이 세 축에 대한 학계·실무 선행 사례를 정리하고, grid fin 설계 권고로 마무리한다.

여기에 조사 도중 기존 하네스 검토에서 드러난 네 번째 난점을 추가한다.

4. 스펙·계획 단계는 **Claude 작성 → Codex 리뷰** 구조로 오류를 검출하는데, 리뷰 지적이 **작성자의 결함인지 리뷰어의 오독인지** 판별되지 않으면 잘못된 교훈이 학습된다 (§7)

§7은 선행 사례가 아니라 cygnus의 **실제 리뷰 산출물 55건을 직접 집계한 1차 관측**에 근거한다.

## 1. 핵심 결론 요약

이 절만 읽어도 전체 그림이 잡히도록 정리했다.

| # | 결론 | 근거 |
|---|---|---|
| 1 | **원시 궤적(raw trajectory)을 저장하는 방식은 이미 폐기된 접근이다.** 실패의 *근본 원인*과 *일반화된 전략*을 추출해 저장해야 한다 | ReasoningBank, MNL, ExpeL 모두 "raw trajectory 저장" 대비 우위를 실증 |
| 2 | **성공만 저장하면 안 된다. 실패가 더 강한 신호다** | ReasoningBank는 성공·실패 양쪽에서 학습해 성공 루틴만 저장하는 방식을 상회 |
| 3 | **유사도 기반 조회는 예방에 실패한다.** 예방하려면 아직 일어나지 않은 일을 검색해야 하므로 쿼리가 존재하지 않는다 | PGR: 관련 사실이 쿼리와 임베딩 거리가 먼 경우가 많음. 예측형 조회로 recall 약 3배 |
| 4 | **조회 결과를 그대로 믿으면 안 된다. 유사도 뒤에 결정론적 게이트가 필요하다** | FailureDNA: 환경 지문(fingerprint) 대조 후 use / inspect / avoid 판정 |
| 5 | **요약·압축은 지식을 파괴한다.** 항목 단위로 증분 갱신해야 한다 | ACE: brevity bias와 context collapse를 명명하고 delta 갱신으로 +10.6% |
| 6 | **비대화는 삭제가 아니라 감쇠와 계층화로 푼다** | Oblivion: 망각 = 삭제가 아닌 접근성 감소. mem0: 망각은 저장 용량이 아니라 회상 품질 문제 |
| 7 | **승격/폐기는 자동화 가능하다. 사람 큐레이션에 의존하면 멈춘다** | learned-behavior: candidate → approved → dormant 자동 전이. cygnus는 수동 큐레이션이라 5월에 정지 |
| 8 | **공용 저장소 아이디어는 타당하며 이미 구현체가 있다.** 단 공유 항목은 신뢰할 수 없는 입력으로 취급해야 한다 | komi-learn 커뮤니티 풀: 서명된 Markdown의 Git 저장소, 회상된 항목은 untrusted로 라벨링 |
| 9 | **스펙 단계에도 diff 대상이 있다 — 독립 리뷰어의 해석이다.** 그리고 그 산출물은 Subject 분류가 이미 끝난 상태로 도착한다 | 리뷰 계약이 스펙 8 + 계획 8 = 고정 16 카테고리를 강제. MNL의 임베딩 클러스터링 단계가 불필요 |
| 10 | **리뷰 지적의 귀속은 물을 필요 없이 관측된다.** 문서 diff 유무 + 다음 라운드 결과로 (A)~(D) 자동 판정 | 리뷰 파일이 타임스탬프로 누적되어 라운드 수가 공짜로 얻어짐 (실측: 3라운드 사례 존재) |
| 11 | **차단하지 않는 신호(NOTE)의 반복이 체계적 약점을 더 잘 드러낸다** | 실측 55건: FAIL 24 vs NOTE 56. 단일 항목에 NOTE 26회 집중, 내용은 거의 동일. 아무것도 학습되지 않음 |
| 12 | **작성자도 리뷰어도 틀리지 않았는데 경고가 반복되는 유형이 있다 — 참조 데이터 낡음** | 실측: `commit-scopes.md`가 프로젝트에 맞게 교체되지 않아 동일 경고 26회. 파일 자체가 교체를 지시하고 있었음 |
| 13 | **"하네스를 고칠까 데이터로 남길까"의 판별 축은 기계 검증 가능성이다.** 그리고 게이트는 회고 시점이 아니라 **승격 임계값 도달 시점**에 실행되어야 한다 | 발생 시점에는 반복 여부를 알 수 없는데 선택이 그 정보에 달려 있음. MNL 배치 클러스터·learned-behavior의 N회/M일과 같은 논리 |
| 14 | **원본 반영이 안 되는 것은 판단 문제가 아니라 인프라 문제였다** | 하네스에 배포 매니페스트(source commit + files[])가 있으나 **해시가 없어 드리프트 검출 불가**. 게다가 gitignore 통짜 무시가 하네스 자신의 추적 정책을 덮음 → 추적 파일 0건 |
| 15 | **(C)/(D)에는 원본에 반영할 diff가 애초에 존재하지 않는다.** 원본 이슈 시스템이 유일한 경로다 | (C)는 하네스 파일을 건드리지 않았고, (D)는 원본에 반영하면 원본 오염. 두 경우 모두 파일 diff로 정보 전달 불가 |
| 16 | **이슈 저장소가 교차 프로젝트 반복성 측정 장치가 된다** | 한 프로젝트 안에서는 표본이 모자라 승격 임계값을 못 정함. 여러 프로젝트의 이슈가 원본에 모이면 라벨별 개수가 곧 승격 신호 |

## 구현 참조 자료 — 외부 자료 정리

> **이 절의 쓰임.** 아래는 이 조사가 확인한 외부 자료를 **구현 시 그대로 참조할 수 있는 형태**로 모은 것이다. §1의 결론 요약과 다르다 — 저쪽은 "무엇을 알아냈나"이고 이쪽은 "무엇을 보고 만들 것인가"다. **본문을 읽지 않고 이 절만 펼쳐도 쓸 수 있게** 정돈했다. 각 항목의 논증과 검증 상태는 괄호 안 절 번호에 있다.

### A. 오류 레코드 스키마 — MNL (ACL 2026 Findings)

메모리 항목은 `e = ⟨s, g, φ(s)⟩` 튜플. `s`=Subject(고수준 클러스터 식별자), `g`=Memory 본체, `φ(s)`=Subject 임베딩. **`Memory(g)`의 5개 필수 구성요소가 이 조사에서 확보한 가장 구체적인 스키마다** (§3.1, 논문 PDF 전문 확인).

| # | 구성요소 | 정의 |
|---|---|---|
| 1 | **Corrected Examples** | 명시적 오답–정답 쌍. 추상화를 구체 사례에 접지 |
| 2 | **Correct Approach** | 적용해야 할 단계별 추론 방법론 |
| 3 | **Mistake Summary** | **근본 원인** 식별 (증상 아님) — 추론 결함·개념 오해·단계 누락·논리 오류 |
| 4 | **Generalizable Strategy** | 재사용 가능한 패턴과 향후 회피 방법 |
| 5 | **Anti-Patterns** | **이 교훈 자체가 오적용되는 시나리오.** 과도한 일반화 방지 장치 |

**5번이 이 조사 범위에서 교훈의 과잉 적용을 다룬 유일한 설계다** — "하지 말 것 목록"이 아니라 "이 규칙을 언제 쓰면 안 되는가"다.

운영 방식도 함께 확인됐다 — **JSONL 파일, 외부 벡터 DB 없음**, bge-m3 임베딩 + 코사인 유사도 + 임계값 + top-k를 시스템 프롬프트에 주입. 갱신은 **유사도 임계값에 따라 병합이 기본 경로**이고 신규 추가가 폴백. **배치 성능이 개선될 때만 외부 메모리에 커밋**한다.

### B. 저장 단위와 학습 신호

| 자료 | 규정 | 확인 상태 |
|---|---|---|
| **ReasoningBank** (Google Cloud AI Research) | 궤적·성공 루틴이 아니라 **일반화 가능한 추론 전략**을 저장. 외부 정답 라벨 없이 자기 판정으로 성공/실패를 가르고 **양쪽 모두에서 학습** | §3.1 |

| **MNL** | **개별 실패가 아니라 배치 클러스터에서 학습.** 단발 실패는 노이즈일 수 있다 | §3.1 |

### C. 컨텍스트 관리 — ACE (Stanford/SambaNova/UC Berkeley)

**두 실패 모드에 이름을 붙였다** (§5.1, 원문 확인).

| 실패 모드 | 내용 |
|---|---|
| **Brevity bias** | 간결한 지시를 선호한 나머지 **도메인 휴리스틱·도구 사용 지침·흔한 실패 모드를 먼저 버린다** |
| **Context collapse** | 반복적으로 전체를 다시 쓰다 보면 세부가 시간이 지나며 침식된다 |

**해법의 형태가 구현 지침이다** — 컨텍스트를 요약 텍스트가 아니라 **진화하는 플레이북**으로 취급한다.

- **3역할**: Generator(궤적 생성) → Reflector(성찰) → Curator(정리)
- **항목화된 플레이북**: **안정적 ID를 가진 순서 있는 항목 목록**, 항목마다 메타데이터
- **증분 델타 갱신**: 전체를 다시 쓰지 않고 항목 단위 추가/수정
- **grow-and-refine**: 늘리되 다듬는다

> **"요약하지 마라"가 이 자료의 핵심 처방이다.** 요약은 정확히 재발 방지에 필요한 정보(실패 모드·도메인 휴리스틱)를 먼저 버린다.

### D. 조회 설계 — 예방적 조회의 네 형태

| 자료 | 메커니즘 | 이 조사에서의 상태 |
|---|---|---|
| **PGR** (UW/Microsoft Research) | 쿼리 대신 **그럴듯한 다음 단계들을 먼저 전개하고 그 목록을 검색 프로브로 사용**. 검색된 사실로 다음 라운드 예측을 개인화 | §4.2, 원문 확인 |
| **FailureDNA** | 유사도 검색 뒤 **결정론적 게이트** — 환경 지문 대조 → `use` / `inspect` / `avoid` 판정을 **에이전트가 결과를 보기 전에** 내린다 | §4.4 |
| **Oblivion** | 읽기 경로를 **에이전트의 불확실성**으로 트리거. 상시 조회의 중복 비용 제거 | §4.5 |
| **ProactAgent** | 조회를 명시적 정책 행동으로 학습 | §4.3. **평가 환경이 SciWorld·AlfWorld·StuLife로 SWE 과제가 아님**(2026-08-02 확인) |

**PGR의 문제 제기가 설계 전제다** — *"실무에서 관련 있는 사실들은 dense retrieval 기준으로 쿼리와 의미적 유사도가 낮은 경우가 많다."* 즉 **정말 필요한 지식일수록 유사도로는 안 걸린다.**

### E. 에피소드 스키마 — FailureDNA

```
episode = { symptoms, environment_fingerprint, action, outcome }
```

**`outcome`을 저장하는 것이 요지다** (§3.2). 증상만 저장하면 과거에 실패한 조치를 유사도가 높다는 이유로 다시 꺼내 쓴다. **`environment_fingerprint`는 과거 해법이 지금도 유효한지 판정하는 결정론적 근거**다.

### F. 승격·감쇠 생애주기 — learned-behavior

가장 이식하기 쉬운 구체적 규칙이다 (§5.3, 원문 확인). 모든 항목이 `confidence` + `status`를 갖고 `candidate → approved → dormant`로 전이한다.

| 전이 | 규칙 |
|---|---|
| **승격** | 최소 N회 관측 + 최소 M일 경과 + **반박 신호 없음** → `approved` |
| **감쇠** | `approved` 항목의 패턴이 X일간 미관측 → 신뢰도 하락 → `dormant`(조언 목록에서 제외) |
| **강화** | 항목이 제시됐고 **그 세션에서 경고한 패턴이 재발하지 않으면** 신뢰도 상승 |

**행동 신호 채굴 대상도 명세로 쓸 수 있다** — 반복 실패, 스킬 우회(전용 스킬이 있는데 원시 명령 실행), **반복적 Edit 자기수정**(계속 `X`를 쓰고 `Y`로 고침 → 규칙은 "처음부터 `Y`"), PreToolUse 차단 반복. LLM을 루프에 넣지 않고 훅 이벤트만으로 얻는다.

### G. 공유·신뢰 경계 — komi-learn

| 설계 요소 | 내용 |
|---|---|
| 저장소 형태 | **서버 없음.** 서명된 Markdown의 GitHub 저장소가 곧 풀 |
| 중복 수렴 | **내용 주소 지정 (BLAKE3)** — 같은 항목이 자동으로 같은 주소로 |
| 신뢰 신호 | **Ed25519 서명.** 서로 다른 계정이 더 많이 서명한 항목이 상위 랭크. **자문 신호일 뿐 강한 신뢰 게이트가 아니라고 명시** |
| **주입 시 취급** | **회상된 커뮤니티 항목은 라벨링되어 신뢰할 수 없는 입력(untrusted)으로 다룬다** |
| **사전 필터** | LLM이 보기 전에 **결정론적으로** 비밀값·머신 고유 경로·일회성 실패·"도구가 고장났다" 류를 거른다 |

## 2. 문제 정의 — 3단계의 오류는 성질이 다르다

### 2.1 오류 = 상위 산출물과의 델타

구현 계획과 구현 단계의 오류는 본질이 같다. **상위 산출물과의 불일치**다.

- 계획 오류 = 스펙과의 불일치
- 구현 오류 = 계획과의 불일치

비교 대상이 파일로 존재하므로 기계적으로 검출 가능하고, 구조화 스키마도 자연스럽게 도출된다(기대값 vs 실제값).

### 2.2 스펙 단계 — 상위 문서는 없지만 diff 대상은 있다

스펙의 "정답"은 사람 머릿속에만 있어 **비교할 상위 문서가 없다.** 여기까지는 사실이다. 그러나 여기서 "그러므로 사후 검출이 불가능하다"는 결론은 나오지 않는다.

**독립적인 두 번째 독자가 diff 대상 역할을 한다.** 작성자의 의도와 독립 리뷰어의 해석 사이의 델타가 스펙 단계의 오류 신호다. 상위 문서 대신 **독립 해석**을 비교 기준으로 삼는 것이다.

기존 하네스(cygnus)가 이미 이 구조로 동작한다. Claude가 스펙과 구현 계획을 작성하고, **Codex가 별도 프로세스로 리뷰**한다(`adapter-codex-review` → `codex exec`). 리뷰 결과는 자유 서술이 아니라 계약(`.harness/contracts/spec-review.md`, `plan-review.md`)으로 고정된 구조를 갖는다.

```markdown
- Decision: READY | READY WITH NOTE | NOT READY

## Checklist
- [PASS|FAIL|NOTE] 1. 목표 명확성 - <evidence>
- [PASS|FAIL|NOTE] 2. Non-goals 명시 - <evidence>
  ... (스펙 8항목 / 계획 8항목)

## Required Fixes
- <NOT READY일 때만>
```

이 산출물은 §3에서 다룬 어떤 학습 입력보다 우수하다. 이유는 §7에서 상술한다. 요지는 **MNL이 임베딩 클러스터링으로 만들어내려던 Subject 분류가 작성 시점에 이미 완료**되어 있다는 것이다 — 스펙 8종 + 계획 8종 = 고정된 16개 카테고리.

사전 차단형 접근도 여전히 유효하며 서로 배타적이지 않다. 요즘IT에 실린 바이버스 AI의 하네스('마에스트로 데브')는 스펙의 모든 항목에 **사람이 결정했는지 AI가 결정했는지를 태깅**하고, AI가 결정한 항목이 하나라도 있으면 전진을 차단해 사람에게 되돌린다. 근거는 "스펙 중 하나라도 AI가 정한 게 있으면 결국 부채로 돌아온다"는 경험이다.

**두 접근은 서로 다른 오류를 잡는다.** 태깅 게이트는 *결정 주체*의 오류(사람이 정해야 할 것을 AI가 정함)를 잡고, 독립 리뷰는 *내용*의 오류(모호·불일치·구현 불가)를 잡는다. grid fin은 둘 다 채택할 수 있다.

**조사 범위에 대한 유의**: 본 조사의 9개 질의는 실패 메모리·자기개선 에이전트·조회 설계·망각/승격·SRE 포스트모템을 겨냥했고, **스펙 단계 또는 요구공학 단계의 오류 검출을 직접 검색한 질의는 없다.** 따라서 위 두 접근이 이 분야의 전부라고 볼 근거는 없다(§9.4 열린 질문 1).

### 2.3 참고: 기존 하네스(cygnus)의 실측

grid fin이 개선하려는 원본 하네스의 실사용 프로젝트를 검토한 결과:

- 학습 루프(`/harness:learn`)가 파이프라인 어디에도 연결되어 있지 않고 순수 수동 → **5월 15일 이후 신규 학습 0건** (이후 세션 로그는 13일치 누적)
- 축적된 학습 9건 중 **4건(44%)이 하네스 자체의 결함**에 관한 것이었으나, 전부 gitignore된 프로젝트 로컬 디렉터리에 갇힘
- 자기 점검 스크립트가 파일 **존재 여부만** 채점 → 루프 정지를 감지하지 못함
- 학습 2건은 실제로 상시 로드 규칙(`component-boundaries.md`, 115줄)으로 승격되었고, 그 파일은 매 세션 컨텍스트에 붙는다 → **비대화가 진행 중**

즉 본 조사의 세 축은 전부 실제로 발생한 문제다. 네 번째 축(리뷰 지적의 귀속)도 마찬가지이며, 그 실측은 §7에 별도로 정리했다.

## 3. 축 1 — 오류를 어떤 스키마로 구조화할 것인가

### 3.1 계보: Reflexion → ExpeL → ReasoningBank → MNL

**Reflexion** (2023)이 출발점이다. 실패 후 자기반성 텍스트를 만들어 다음 시도에 넣는다. 한계는 반성이 **그 태스크 안에서만** 유효하다는 것이다.

**ExpeL** (AAAI 2024)은 이를 태스크 경계 밖으로 확장했다. 3단계로 동작한다.

1. **경험 수집** — 시행착오로 성공·실패 궤적을 경험 풀에 축적
2. **인사이트 추출** — 성공/실패 쌍 또는 성공 목록을 놓고 자연어 인사이트 목록을 갱신
3. **적용** — 추론 시 인사이트 + 유사 성공 궤적을 컨텍스트에 주입

핵심은 인사이트를 갱신하는 **4개 연산**이다: `ADD`, `EDIT`, `UPVOTE`, `DOWNVOTE`. 지식이 단순히 쌓이는 게 아니라 **투표로 중요도가 오르내리고 편집으로 다듬어진다.** 파라미터 업데이트 없이 학습한다.

**ReasoningBank** (Google Cloud AI Research, 2025)은 여기서 두 가지를 더한다.

- 궤적이나 성공 루틴이 아니라 **일반화 가능한 추론 전략**을 저장한다. 저장 단위가 "무엇을 했는가"가 아니라 "왜 그렇게 판단해야 하는가"다.
- 외부 정답 라벨 없이 **에이전트의 자기 판정**으로 성공/실패를 가르고, 양쪽 모두에서 학습한다.

논문의 실증 결과: 원시 궤적을 저장하거나 성공 루틴만 저장하는 기존 메모리 기법을 웹 브라우징·소프트웨어 엔지니어링 벤치마크에서 일관되게 상회했다. 여기에 **MaTTS(memory-aware test-time scaling)**를 붙여, 태스크당 연산을 더 써서 다양한 경험을 생성하면 대조 신호가 풍부해져 더 좋은 메모리가 만들어지고, 그 메모리가 다시 스케일링을 효율화하는 상승 작용을 보였다.

**MNL (Mistake Notebook Learning)** (ACL 2026 Findings)은 오류 전용 스키마를 명시한 유일한 사례다. 배치 단위 실패를 **주제별로 클러스터링**해 공통 오류 패턴을 "오답 노트"로 증류한다.

메모리 항목은 `e = ⟨s, g, φ(s)⟩` 튜플이다.

- **Subject(s)** — 고수준 의미 클러스터 식별자. 예: `"SQL: Join conditions on null values"`. 광범위한 주제 매칭을 가능하게 한다
- **Memory(g)** — 실행가능성과 안전성을 보장하는 **5개 필수 구성요소** (아래)
- **φ(s)** — Subject의 임베딩 벡터. 사전 계산해 조회에 사용

`Memory(g)`의 5개 구성요소는 다음과 같다 (논문 원문 기준).

| # | 구성요소 | 정의 |
|---|---|---|
| 1 | **Corrected Examples** | 명시적인 오답–정답 쌍. 추상화를 구체 사례에 접지(ground)시킨다 |
| 2 | **Correct Approach** | 적용해야 할 단계별 추론 방법론 |
| 3 | **Mistake Summary** | **오류의 근본 원인**을 식별 (추론 결함, 개념 오해, 단계 누락, 논리 오류 등) |
| 4 | **Generalizable Strategy** | 재사용 가능한 문제 해결 패턴과 향후 회피 방법 |
| 5 | **Anti-Patterns** | 오적용 시나리오를 명시하는 결정적 경고. **과도한 일반화(over-generalization)를 방지**하기 위한 것 |

5번의 목적이 특히 중요하다. Anti-Patterns는 "하지 말 것"의 목록이 아니라 **이 교훈 자체가 남용되는 것을 막는 장치**다. 학습이 쌓일수록 과잉 적용으로 오히려 성능을 해치는 문제를 정면으로 다룬 유일한 설계다.

구현 세부도 참고할 만하다.

- 메모리는 **JSONL 파일**로 유지하며 **외부 벡터 DB를 쓰지 않는다.** bge-m3 임베딩 + 코사인 유사도 + 임계값 필터 + top-k를 시스템 프롬프트에 주입하는 경량 구성이다
- **메모리 갱신은 유사도 임계값에 따라 기존 항목과 병합하거나 새로 추가한다** — 병합이 기본 경로다
- **개별 실패가 아니라 배치 클러스터에서 학습한다.** 단발 실패는 노이즈일 수 있으나, 주제별로 묶으면 공통 원인이 드러난다
- **배치 성능이 개선될 때만 외부 메모리에 커밋한다.** 학습이 오히려 성능을 떨어뜨리는 것을 막는 안전장치다. cygnus에는 이런 검증이 전혀 없다

### 3.2 실무 스키마: FailureDNA

인시던트 대응 에이전트용 메모리 시스템으로, 학계 논문보다 스키마가 구체적이다. 각 사건을 **에피소드**로 저장한다.

```
episode = {
  symptoms,               # 증상
  environment_fingerprint,# 환경 지문 — 이 수정이 여전히 유효한지 판정하는 근거
  action,                 # 취한 조치
  outcome                 # 실제 결과 (성공/실패)
}
```

핵심 통찰은 **"결과(outcome)를 저장한다"**는 것이다. 증상만 저장하면, 과거에 실패한 조치를 유사도가 높다는 이유로 다시 꺼내 쓴다. FailureDNA의 문제 제기가 정확히 이것이다 — *"장애가 익숙해 보이면 순진한 에이전트는 가장 유사한 과거 사건을 꺼내 그 조치를 재사용한다. 지난번에 실패한 조치였더라도."*

**environment_fingerprint**는 grid fin에 직접 이식할 가치가 있다. 과거의 해법이 지금도 유효한지 판정하는 결정론적 근거다.

### 3.3 실무 스키마: learned-behavior — 자기 보고 없이 행동 신호만

`lisn0/learned-behavior`는 접근이 다르다. **LLM을 루프에 넣지 않고 훅 이벤트에서 순수 행동 신호만 채굴한다.**

포착 대상:

- **반복 실패** — 세션을 넘나들며 같은 에러 패턴이 재발
- **스킬 우회** — 전용 스킬이 있는데도 원시 명령을 직접 실행
- **반복적 Edit 자기수정** — 에이전트가 계속 `X`를 쓰고 `Y`로 고침 → 규칙은 "다음엔 처음부터 `Y`를 써라"
- **PreToolUse 차단** — 가드가 명령을 막을 때마다 기록. 반복 차단은 훈련 공백을 드러냄

이 목록은 그대로 **grid fin의 구현 단계 오류 검출기 명세**로 쓸 수 있다. 특히 "반복적 Edit 자기수정"은 별도 계측 없이 훅만으로 잡히는 고신호 지표다.

주의할 점: 이 방식은 **구현 단계**에는 잘 맞지만 스펙·계획 단계에는 맞지 않는다. 그 단계에서는 도구 호출이 아니라 문서 간 델타가 신호이기 때문이다.

### 3.4 축 1 권고 스키마

위 사례를 종합하면 grid fin의 오류 레코드는 다음을 갖춰야 한다.

```yaml
id:                          # 내용 주소 지정 권장 (중복 병합용)
subject:                     # 고수준 클러스터 식별자              ← MNL Subject(s)
stage: spec|plan|impl        # 발생 단계
trigger:                     # ← 축 2의 조회 키. 필수
  module:                    # 대상 모듈/파일군
  operation:                 # 신규|변경|삭제|마이그레이션 등
  tech:                      # 기술 스택 태그
corrected_examples:          # 오답–정답 쌍 (구체 접지)            ← MNL 1
correct_approach:            # 단계별 올바른 방법론                ← MNL 2
mistake_summary:             # 근본 원인 (증상 아님)               ← MNL 3
generalizable_strategy:      # 재사용 가능 전략                    ← MNL 4
anti_patterns:               # 이 교훈의 오적용 시나리오            ← MNL 5
environment_fingerprint:     # 유효성 판정 근거                    ← FailureDNA
outcome:                     # 이 해법의 실제 결과                 ← FailureDNA
destination: harness|shared|local   # ← 축 4. 필수
confidence:                  # 신뢰도 점수                        ← 축 3
status: candidate|approved|dormant  # ← 축 3
observations:                # 관측 횟수
last_seen:                   # 감쇠 계산용
```

`anti_patterns`를 빠뜨리기 쉬운데, 이 필드가 **교훈의 과잉 적용을 막는 유일한 장치**다. 축적된 규칙이 엉뚱한 상황에 적용되어 오히려 해가 되는 것은 비대화 못지않게 실질적인 위험이다.

`trigger`와 `destination`을 **필수 필드로 강제**하는 것이 이 스키마의 핵심이다. 전자가 없으면 조회되지 않고, 후자가 없으면 전부 로컬에 쌓인다.

## 4. 축 2 — 언제 어떻게 꺼내 쓸 것인가 (예방적 조회)

이 축이 가장 어렵고, 실패도 가장 많은 지점이다.

### 4.1 문제: 예방에는 검색 쿼리가 없다

오류가 이미 터졌다면 에러 메시지라는 검색어가 있다. 그러나 **예방하려면 아직 일어나지 않은 일을 검색해야 한다.** 표준 RAG와 GraphRAG는 전부 **회고적(retrospective)** 이다 — 쿼리와의 임베딩 유사도나 고정된 그래프 순회에 의존한다.

PGR 논문의 관찰이 결정적이다: *"실무에서 관련 있는 사실들은 dense retrieval 기준으로 쿼리와 의미적 유사도가 낮은 경우가 많다."* 즉 **정말 필요한 지식일수록 유사도로는 안 걸린다.**

cygnus 데이터가 이를 뒷받침한다. 그 하네스는 모든 학습 항목에 `## When to Activate`(트리거 명세)를 필수로 요구했고 9건 전부 이를 갖췄다. 그런데도 그중 하나라도 실제로 회상된 적이 있는지 검증된 바가 없다. **트리거를 잘 쓰는 것은 필요조건이지 충분조건이 아니다.** description 매칭에 기대는 조회는 "모델이 마침 떠올려주기를 바라는" 구조다.

### 4.2 해법 A — PGR: 미래를 상상해 그것을 검색어로 쓴다

**Prospection-Guided Retrieval** (University of Washington + Microsoft Research, 2026)은 인간의 **예측(prospection)** — 상상한 미래를 회상의 단서로 쓰는 능력 — 에서 착안했다.

동작 방식:

1. 쿼리(목표)를 받으면 먼저 **그럴듯한 다음 단계들**을 Tree-of-Thought 또는 선형 체인으로 전개한다
2. 원래 쿼리 대신 **이 단계들을 검색 프로브로 사용**한다
3. 검색된 사실로 다음 라운드의 예측을 개인화한다 → 시뮬레이션이 실제 이력에 근거하게 되면서 비로소 관련성이 드러나는 기억까지 도달한다

결과: MemoryQuest 벤치마크에서 최강 베이스라인 대비 **recall 약 3배**. LLM-as-judge 쌍대 비교에서 89~98% 선호.

**grid fin 적용**: 스펙/계획 단계 진입 시 "이 작업에서 앞으로 무슨 단계를 밟게 될까"를 먼저 전개하고, 그 단계 목록을 오류 저장소 조회 키로 쓴다. 이는 "작업 좌표(단계 × 모듈 × 작업 유형)로 키잉한다"는 아이디어의 정교한 형태다.

### 4.3 해법 B — ProactAgent: 조회 자체를 정책 행동으로

**"Ask Only When Needed"** (ECNU + Shanghai AI Lab, 2026)의 문제 제기: 기존 방법은 **수동적으로** 조회한다 — 태스크 시작 시점이나 매 스텝마다. 그래서 **상호작용 도중에 발생하는 지식 공백을 놓친다.**

해법(`PROACTRL`)은 조회를 명시적 정책 행동으로 취급하고, **언제 무엇을 조회할지를 학습**시킨다. 동일한 상호작용 접두사에서 조회를 한 경우와 안 한 경우의 연속을 짝지어 비교하고, 조회가 결과나 효율을 실제로 개선했을 때만 보상을 준다.

결과: 성공률 최대 32% 상대 개선, 상호작용 라운드 33% 이상 감소.

> **2026-08-02 출처 감사 — 수치는 확인됐고, 적용 범위에 유의가 붙는다.** 최초 작성 시 이 수치는 검색 엔진의 LLM 생성 요약에 근거했다. 원문 초록을 직접 확인한 결과 표기는 정확하다 — *"up to 32% relative improvement in success rate and over 33% reduction in interaction rounds"*. 다만 두 가지가 드러났다.
>
> 1. **초록이 베이스라인을 특정하지 않는다.** "최대 32%"가 무엇 대비인지 초록만으로는 알 수 없다.
> 2. **평가 환경이 SciWorld · AlfWorld · StuLife다** — 가정·과학 실험 시뮬레이션 계열의 체화(embodied) 에이전트 벤치마크이고 **소프트웨어 엔지니어링 과제가 아니다.**
>
> 2번이 이 문서의 사용 방식에 직접 걸린다. 본 조사는 이 논문을 **코딩 하네스의 조회 시점 설계** 근거로 끌어 쓰고 있는데, 원 실험은 다른 도메인이다. **아이디어(조회를 정책 행동으로 다루고 그 효용을 측정한다)는 도메인 무관하게 이전되지만, 수치는 이전되지 않는다.** 권고 #21이 강화학습이 아니라 "조회가 도움이 됐는지 기록"으로 축소된 것은 결과적으로 이 한계와 부합한다.

**grid fin 적용**: 강화학습은 과하지만, **"조회가 도움이 됐는지"를 기록하는 것**은 가능하다. 조회 결과를 주입한 세션에서 해당 오류가 재발하지 않았다면 그 항목의 신뢰도를 올린다(→ 축 3의 reinforcement).

### 4.4 해법 C — FailureDNA: 유사도 뒤에 결정론적 게이트

가장 실용적인 안전장치다. 조회는 하이브리드(시맨틱 + 키워드)로 하되, 그 결과를 바로 쓰지 않는다.

```
검색 → 환경 지문 대조 → 결정론적 판정: use | inspect | avoid → 허용 목록으로 좁힘 → 에이전트에 제시
```

**판정이 에이전트가 결과를 보기 전에 내려진다**는 점이 핵심이다. 모델이 무효한 기억에 근거해 행동하는 것을 구조적으로 막는다.

**grid fin 적용**: 조회된 오류 항목에 대해 "이 항목의 `environment_fingerprint`가 현재 환경과 일치하는가"를 코드로 판정하고, 불일치 항목은 `avoid`로 라벨링해 제시하거나 아예 제외한다. LLM 판단에 맡기지 않는다.

### 4.5 해법 D — Oblivion: 언제 조회할지를 불확실성으로 결정

**Oblivion**은 메모리 제어를 읽기 경로와 쓰기 경로로 분리한다.

- **읽기 경로**: 에이전트의 **불확실성**과 현재 버퍼의 충분성을 근거로 메모리를 조회할지 결정 → "always-on" 조회의 중복 비용 제거
- **쓰기 경로**: 응답 형성에 기여한 기억을 **강화**

결과적으로 **고수준 전략은 상시 유지하고 세부는 필요할 때 동적 로드**하는 계층 구조가 만들어진다. 이는 축 3의 비대화 문제와 직결된다.

### 4.6 축 2 권고

grid fin에는 **4중 조회 구조**를 권고한다.

| 계층 | 시점 | 방식 |
|---|---|---|
| 1. 상시 | 매 세션 | 고빈도·고비용 항목만 규칙으로 상시 로드 (엄격한 승격 기준 적용) |
| 2. 단계 진입 | spec/plan/impl 시작 시 **필수** | 작업 좌표 키로 결정론적 조회. 모델의 연상에 맡기지 않음 |
| 3. 예측 기반 | 단계 진입 시 (2와 결합) | 다음 단계를 전개해 그 목록을 추가 프로브로 사용 (PGR) |
| 4. 게이트 | 조회 직후 | 환경 지문 대조 → use/inspect/avoid 판정 (FailureDNA) |

계층 2가 이 설계의 심장이다. **필수 스텝으로 파이프라인에 박아야 한다.** 선택적으로 만들면 안 돈다 — cygnus에서 실증되었다.

## 5. 축 3 — 비대화, 승격과 폐기

### 5.1 ACE: 요약이 지식을 파괴한다

**Agentic Context Engineering** (Stanford + SambaNova + UC Berkeley, 2025년 10월)이 이 축의 기준 문헌이다. 두 가지 실패 모드를 명명했다.

- **Brevity bias (간결성 편향)** — 프롬프트 최적화기들이 간결하고 범용적인 지시를 선호한 나머지, **도메인 특화 휴리스틱·도구 사용 지침·흔한 실패 모드를 버린다.** 논문은 GEPA가 간결성을 장점으로 내세우는 것을 직접 반례로 든다.
- **Context collapse (컨텍스트 붕괴)** — 반복적으로 전체를 다시 쓰다 보면 세부가 시간이 지나며 침식된다.

ACE의 해법은 컨텍스트를 요약된 텍스트가 아니라 **진화하는 플레이북(playbook)** 으로 취급하는 것이다.

- **3역할 구조**: Generator(궤적 생성) → Reflector(성찰) → Curator(정리)
- **항목화된 플레이북**: 안정적인 ID를 가진 순서 있는 항목 목록. 항목마다 메타데이터 보유
- **증분 델타 갱신**: 전체를 다시 쓰지 않고 항목 단위로 추가/수정 → 붕괴 방지
- **grow-and-refine 원칙**: 늘리되 다듬는다

성과: 에이전트 벤치마크 +10.6%, 금융 도메인 +8.6%, 적응 지연시간과 롤아웃 비용 대폭 감소. AppWorld 리더보드에서 **더 작은 오픈소스 모델로 프로덕션급 1위 에이전트와 동률**, 어려운 test-challenge 분할에서는 상회. 라벨 없이 자연스러운 실행 피드백만으로 적응했다.

**grid fin에 주는 함의가 크다.** "학습이 쌓이면 하네스가 비대해진다"는 걱정에 대한 답은 **"요약해서 줄이자"가 아니다.** 요약은 정확히 재발 방지에 필요한 정보(실패 모드, 도메인 휴리스틱)를 먼저 버린다. 답은 **항목화 + 안정적 ID + 델타 갱신**이다.

### 5.2 감쇠와 망각 — 삭제가 아니라 접근성 조절

**Oblivion**의 정의: 망각은 **삭제가 아니라 접근성의 감소**다. 인간 기억이 그렇듯, 시간이 지나면 덜 접근 가능해지지만 강화나 맥락 단서로 재활성화될 수 있다.

**mem0**의 관점이 더 직관적이다: *"전부 보관하면 간섭 때문에 회상 품질이 떨어진다. 저장된 사실이 많을수록 올바른 것을 꺼내기 어려워진다. 망각은 저장 용량 문제가 아니라 회상 품질 설계 문제다."*

**SF-AMS**는 정적 검색과 휴리스틱 감쇠를 **효용 기반 생존 메커니즘**으로 대체한다.

세 문헌의 공통 결론: **폐기 기준이 없는 지식 저장소는 커질수록 나빠진다.** 이는 cygnus에서 관측된 현상과 일치한다 — 큐레이션이 "명시 요청 시에만" 돌게 설계되어 한 번도 실행되지 않았고, 그 결과 승격된 항목의 원본이 중복으로 남고 `/dev:*`처럼 존재하지 않는 커맨드를 참조하는 화석 항목이 그대로 조회 대상에 남아 있다.

### 5.3 자동 승격 — learned-behavior의 생애주기

가장 이식하기 쉬운 구체적 규칙이다. 모든 학습 항목이 `confidence` 점수와 `status`를 갖는다: `candidate` → `approved` → `dormant`.

| 전이 | 규칙 |
|---|---|
| **승격 (Promotion)** | 최소 N회 이상 관측 + 최소 M일 이상 경과 + 반박 신호 없음 → `approved` |
| **감쇠 (Decay)** | `approved` 항목의 패턴이 X일간 관측되지 않으면 신뢰도 하락 → 결국 `dormant`가 되어 조언 목록에서 제외 |
| **강화 (Reinforcement)** | 항목이 제시되었고 그 세션에서 경고한 패턴이 재발하지 않으면 신뢰도 상승 |

`promote`와 `decay`를 야간 배치(cron 또는 Stop 훅)로 돌리면 **사람 큐레이션 없이 코퍼스가 개선된다.**

강화 규칙이 특히 좋다. **"조회가 실제로 효과가 있었는가"를 측정하는 유일한 실무 사례**이며, ProactAgent가 강화학습으로 하는 일을 훨씬 싸게 근사한다.

### 5.4 축 3 권고

1. **승격 기준을 명시한다.** 축은 **빈도 × 실패 비용**. 자주 발생하고 대가가 큰 것만 상시 로드로 올린다.
2. **상시 로드 계층에 예산을 건다.** 예: "규칙 파일 총합 500줄" 같은 상한. 초과하면 새 항목을 넣기 전에 기존 항목을 내려야 한다. cygnus의 `component-boundaries.md`는 상한이 없어 계속 자라고 있다.
3. **요약하지 않는다.** 항목화 + 안정적 ID + 델타 갱신으로 관리한다 (ACE).
4. **감쇠를 자동화한다.** `learned-behavior`의 3규칙을 그대로 채택하되, 개인용이므로 임계값은 느슨하게 시작한다.
5. **승격된 항목의 원본을 제거하는 규칙을 명시한다.** cygnus에 없어서 실제로 중복이 발생했다.
6. **학습 커밋 전 검증.** MNL처럼 "성능이 개선될 때만 커밋"이 이상적이나 개인 하네스에서는 측정이 어렵다. 최소한 **새 항목이 기존 규칙과 모순되지 않는지** 확인하는 단계는 넣는다.

## 6. 축 4 — 프로젝트를 넘어선 공유 (공용 저장소)

### 6.1 먼저: 목적지가 하나가 아니다

공용 저장소를 만들기 전에 **분류가 먼저**다. cygnus의 학습 9건을 성격별로 가르면 깨끗하게 나뉜다.

| 목적지 | 성격 | cygnus 실측 | 예 |
|---|---|---|---|
| **하네스 원본** | 하네스 컴포넌트 자체의 결함·누락 | 4건 (44%) | 상태 테이블 게이트 패턴, 체크리스트 중복 위반 |
| **공용 저장소** | 프로젝트 무관 기술 일반 지식 | 5건 (56%) | `set -u`에서 빈 배열 확장, `.gitignore` 디렉터리 negation, HEREDOC 인젝션 방어 |
| **프로젝트 로컬** | 이 코드베이스 고유 도메인 규칙 | 0건 | — |

**학습의 44%가 하네스 레벨 지식이었는데 전부 gitignore된 프로젝트 디렉터리에 갇혀 있었다.** 우려하던 문제가 그대로 실측된 것이다.

여기서 나오는 설계 요구사항: **회고 단계에서 목적지 분류를 강제한다.** 분류 필드가 필수가 아니면 전부 로컬에 쌓인다. 공용 저장소 자체보다 이 분류가 먼저다.

### 6.2 실무 사례: komi-learn 커뮤니티 풀

조사 범위에서 **공용 저장소 아이디어를 가장 완성도 높게 구현한 사례**다. 설계가 참고할 만하다.

- **서버 없음.** 서명된 Markdown 파일들의 **GitHub 저장소**가 곧 풀이다
- **선택적 참여.** 일반적 교훈만 기여 가능하고, 각 기여는 **본인이 검토한 PR을 연다**
- **내용 주소 지정** — BLAKE3 해시. 중복 항목이 자동으로 같은 주소로 수렴한다
- **서명** — Ed25519. 서로 다른 GitHub 계정이 더 많이 서명한 항목이 pull 시 상위 랭크
- **Sybil 저항적이나 Sybil-proof는 아님**을 명시하고, 랭킹을 **자문 신호일 뿐 강한 신뢰 게이트가 아니라고** 규정
- **회상된 커뮤니티 항목은 라벨링되어 신뢰할 수 없는 입력(untrusted input)으로 취급**된다

마지막 항목이 보안상 결정적이다. 공용 저장소의 항목은 결국 **에이전트 컨텍스트에 주입되는 외부 텍스트**이므로 프롬프트 인젝션 벡터다. 개인용이라 남의 항목을 안 받더라도, **자기 프로젝트의 자동 추출 결과를 다른 프로젝트에 주입하는 것 자체가 신뢰 경계를 넘는 행위**다.

komi-learn은 또한 **LLM이 보기 전에 결정론적 필터**로 비밀값, 머신 고유 경로, 일회성 실패, "도구 X가 고장났다" 류의 불평을 걸러낸다. 이 사전 필터는 그대로 채택할 가치가 있다.

### 6.4 축 4 권고

1. **분류를 먼저, 저장소는 그 다음.** 오류 레코드에 `destination` 필수 필드를 두고 회고 단계에서 반드시 판정한다.
2. **`destination: harness`인 항목은 별도 큐로 뺀다.** 이것이 하네스 개선 백로그다. grid fin 저장소에 이슈나 파일로 쌓이게 하고, 프로젝트 로컬에 남지 않게 한다.
3. **공용 저장소는 Git + Markdown + frontmatter**로 시작한다. 조회는 `trigger` 필드에 대한 결정론적 매칭 + grep으로 충분하다. 규모가 커지면 그때 색인을 붙인다.
4. **쓰기 시점에 기존 항목을 먼저 조회해 병합을 기본으로 한다.** 신규 생성은 병합 실패 시의 폴백이다. 내용 주소 지정(해시)이 이를 돕는다.
5. **주입되는 공유 항목은 신뢰할 수 없는 입력으로 취급한다.** 비밀값·절대경로·일회성 실패는 LLM에 닿기 전에 결정론적으로 거른다.

## 7. 축 5 — 리뷰 지적에서 하네스 개선까지 (스펙·계획 단계)

> **이 절의 위치.** 아래는 기존 하네스(cygnus) 실측이며 **위 자료가 이 프로젝트에 해당하는지, 어느 축이 급한지를 가늠하는 보조 근거**다. 구현 시 참조할 재료는 「구현 참조 자료」 절에 모여 있다. 다만 이 절에는 문헌에 없는 것이 하나 있다 — **(A)~(D) 귀속 분류**는 리뷰 산출물 55건을 직접 집계해 도출한 것이고 선행 사례를 찾지 못했다.

§2.2에서 정리했듯 스펙·계획 단계의 오류 신호는 **독립 리뷰어와의 해석 델타**다. 기존 하네스(cygnus)는 Claude가 작성하고 Codex가 리뷰하는 구조를 이미 갖추고 있다.

이 절은 그 리뷰 지적이 하네스 개선으로 이어지기까지의 **전 경로**를 다룬다. 네 단계이며 각각이 독립적으로 끊길 수 있다.

| 단계 | 질문 | 소절 |
|---|---|---|
| 1. **귀속** | 누가 틀렸는가 — 작성자? 리뷰어? 참조 데이터? | §7.1 ~ §7.7 |
| 2. **조치 선택** | 하네스를 고칠 것인가, 데이터로 남길 것인가 | §7.8 |
| 3. **원본 반영** | 고친 것이 원본에 어떻게 도달하는가 | §7.9 |
| 4. **리포팅** | 고칠 파일이 없을 때 무엇을 전달하는가 | §7.10 |

cygnus에서는 1단계에서 이미 끊겨 있었다. 나머지 세 단계는 그 지점이 뚫렸을 때 곧바로 마주치는 문제다.

> §7.1~7.6과 §7.9.1~7.9.2는 cygnus 저장소를 직접 읽어 얻은 **1차 관측**이다. §7.8, §7.9.3 이후, §7.10은 그 관측 위에 세운 **설계 제안**이며 검증되지 않았다. 구분은 부록 A 참조.

### 7.1 리뷰 산출물은 이미 최상급 학습 입력이다

계약으로 고정된 리뷰 리포트의 구조가 §3에서 검토한 어떤 입력보다 낫다. 이유는 세 가지다.

1. **Subject 분류가 작성 시점에 완료된다.** MNL은 임베딩(bge-m3) + 코사인 유사도로 실패를 주제별 클러스터링하지만, 리뷰 체크리스트는 **스펙 8항목 + 계획 8항목 = 고정 16 카테고리**로 이미 분류되어 도착한다. 임베딩도 클러스터링도 불필요하다.
2. **판정이 3단계로 등급화되어 있다.** `PASS` / `NOTE` / `FAIL` + `Decision: READY | READY WITH NOTE | NOT READY`. 신호 강도가 이미 인코딩되어 있다.
3. **evidence가 함께 온다.** 체크리스트 각 줄이 판정 근거를 포함하므로 MNL의 `Corrected Examples`(구체 접지) 항목을 바로 채운다.

세션 도구 호출 로그(jsonl)에서 실수를 *추론*하는 §3.3 방식과 비교하면 신호 대 잡음비가 비교되지 않는다.

### 7.2 결정적 결손 — 해소 결과가 어디에도 기록되지 않는다

리뷰 파일은 **무엇이 지적되었는지**를 기록한다. 그러나 그 지적이 어떻게 끝났는지는 기록하지 않는다.

`NOT READY` → Claude가 `spec:drafting`으로 롤백 → 수정 → 재리뷰. 이 사이클에서 다음이 소실된다.

- 이것이 **Claude의 작성 결함**이었는가, **Codex의 오독**이었는가
- 문서를 고쳐서 통과했는가, 고치지 않고 통과했는가

이 정보 없이 리뷰 지적을 학습에 넣으면 **잘못된 교훈이 규칙으로 승격**된다. 그리고 그 규칙이 다음 스펙을 왜곡하고 다시 리뷰에 걸리는 자기강화 고리가 생긴다.

### 7.3 귀속 판정 — 묻지 말고 관측한다

"누가 판정하는가"가 이 설계의 난제다. Claude가 판정하면 자기 작성물을 방어하고, Codex가 판정하면 자기 지적을 방어한다. 제3의 판정자나 사람을 매번 부르는 것은 비용이 크다.

해법은 **판정을 묻지 않고 관측하는 것**이다. 리뷰 이후 대상 문서에 diff가 있었는지, 그리고 다음 라운드 결과가 무엇인지만 보면 된다. 둘 다 이미 자동 관측 가능하다 — 리뷰 파일이 `spec-review-<YYMMDDHHmmss>.md` 형태로 **타임스탬프 누적**되므로 라운드 수도 공짜로 얻어진다.

| 관측 | 귀속 | 목적지 | 조치 |
|---|---|---|---|
| diff 있음 + **내용** 변경 | **(A) 작성 결함** | 학습 | 스펙/계획 작성 규칙으로 |
| diff 있음 + **표현만** 명확화 | **(B) 모호성 결함** | 학습 | 명확성 축 작성 규칙으로 |
| diff 없음 + 다음 리뷰 통과 | **(C) 리뷰어 오독** | `harness` | 리뷰어 프롬프트·컨텍스트 수정 |
| diff 없음 + 동일 항목 재차 FAIL | **(C) 확정** | `harness` | 루프 브레이커 + 사람 개입 |
| diff 없음 + 여러 토픽에서 동일 NOTE 반복 | **(D) 참조 데이터 낡음** | `harness` | 참조 파일 갱신 (§7.5) |

**(A)와 (B) 모두 학습 대상이라는 점이 중요하다.** 리뷰어가 오해했더라도 그 원인이 스펙의 모호함이라면 그것은 여전히 작성 결함이다. 종류가 다를 뿐이다.

실제 사례로 `membership-invite` 토픽의 plan-review는 `NOT READY → NOT READY → READY WITH NOTE`로 3라운드를 돌았다. 라운드 수와 각 라운드의 문서 diff를 보면 위 표로 자동 분류된다.

### 7.4 오염 사례 — (C)가 분류 없이 저장되면 화석이 된다

cygnus의 learned 스킬 `spec-review-pending-pr-dependency`가 실증 사례다.

> *"Codex spec-review가 미병합 PR의 파일을 '없음'으로 판단해 NOT READY를 반복할 때의 해결 패턴"*

Codex가 실제 파일시스템을 확인하는 탓에, 아직 병합되지 않은 PR에서 추가될 파일을 참조하는 스펙에 대해 반복적으로 `NOT READY`를 냈다. **명백한 (C)** — 스펙의 결함이 아니라 리뷰어의 한계다.

이 학습은 "해결 패턴"(= 우회법)으로 저장되었고, **리뷰어 결함이라는 사실은 어디에도 기록되지 않았다.** 그 결과 지식이 "리뷰어를 고쳐야 한다"가 아니라 "이럴 땐 이렇게 피해 가라"로 화석화됐다. 귀속 필드가 없으면 (C)는 영구적 우회 지식이 된다.

### 7.5 실측 — 가장 강한 신호는 FAIL이 아니라 반복되는 NOTE였다

리뷰 파일 55건 집계 결과다.

| Decision | 건수 |
|---|---|
| READY WITH NOTE | 37 |
| NOT READY | 13 |
| READY | 5 |

FAIL 총 24회, NOTE 총 56회. 항목별 분포는 극심하게 편중되어 있다.

| 체크리스트 항목 | FAIL | NOTE |
|---|---|---|
| 완료 기준 명확성 (계획 #4) | 1 | **26** |
| 범위 적정성 (스펙 #8) | 0 | 11 |
| 구현 가능성 (스펙 #7) | 6 | 6 |
| Story 타입 정확성 (계획 #5) | 5 | 0 |
| 내부 일관성 (스펙 #6) | 4 | 2 |
| Open Questions (스펙 #5) | 3 | 4 |

**1위 항목의 NOTE 26건을 열어보면 거의 매번 같은 두 가지다** — commit scope가 `.harness/commit-scopes.md` 권장 목록에 없음, Task first-line subject가 권장 80자 초과.

`NOTE`는 non-blocking이므로 매번 그대로 통과했다. 그 결과 **26회 반복되는 동안 아무것도 학습되지 않았다.** 55건의 리뷰에서 가장 명확한 체계적 약점 신호였는데, 정확히 그것만 아무도 소비하지 않았다.

이는 설계 결론이지 통계가 아니다: **차단하는 신호(FAIL)보다 차단하지 않는 신호(NOTE)의 반복이 체계적 약점을 더 잘 드러낸다.** FAIL은 그 지점에서 고쳐지므로 반복되지 않는다. NOTE는 고쳐지지 않으므로 반복되고, 반복 자체가 신호다.

### 7.6 (D) 유형의 발견 — 셋 다 틀리지 않았는데 26번 경고가 났다

위 26건의 정체를 확인한 결과 (A)도 (C)도 아니었다.

`.harness/commit-scopes.md`가 정의한 스코프는 `agent`, `skill`, `command`, `rule`, `hook`, `script`, `contract`, `template`, `docs`, `harness` — **하네스 자체를 개발할 때 쓰는 목록**이다. 그러나 cygnus는 Flutter/Firebase 응용 프로젝트이고 실제 사용 스코프는 `shared`, `backend`, `parent_app`, `child_app`, `app_core`다.

그 파일 자체가 이렇게 명시하고 있다.

> **하네스를 다른 프로젝트로 복사할 때는 이 파일을 프로젝트 구조에 맞게 교체한다.**

교체하라고 파일에 적혀 있으나 교체되지 않았다(mtime 5월 6일 = 하네스 일괄 설치 시점). 그리고 plan-review가 26번 같은 경고를 냈다.

정리하면 — **Codex의 지적은 정확했고(스코프가 목록에 없는 것은 사실), Claude의 작성도 정확했으며(프로젝트 구조상 맞는 스코프), 틀린 것은 하네스의 참조 데이터였다.**

2분법((A) 작성자 결함 / (C) 리뷰어 오독)으로도, 여기에 (B)를 더해도 잡히지 않는 네 번째 유형이다.

| 유형 | 실질 | 판별 신호 |
|---|---|---|
| (A) | Claude 작성 결함 | diff 있음 + 내용 변경 |
| (B) | 스펙 모호성 | diff 있음 + 표현만 변경 |
| (C) | 리뷰어 오독 | diff 없음 + 통과 또는 반복 FAIL |
| **(D)** | **참조 데이터 낡음** | **diff 없음 + 여러 토픽에서 동일 NOTE 반복** |

(C)와 (D)의 차이는 "지적 내용이 사실인가"인데, 이를 직접 판정하기는 어렵다. **토픽 간 반복성이 실용적 대리 지표**가 된다 — 여러 토픽에서 동일하게 재현되는 지적은 리뷰어의 우발적 오독이 아니라 참조 데이터의 체계적 불일치일 가능성이 높다.

### 7.7 축 5 권고

1. **리뷰 지적마다 `resolution` 필드를 필수화**하고, §7.3의 표에 따라 diff 관측으로 (A)~(D)를 자동 판정한다.
2. **NOTE를 폐기하지 않는다.** 토픽 간 교차 집계로 동일 항목 반복 횟수를 세고, 임계값을 넘으면 승격 후보로 올린다. 26회를 놓친 것이 이 하네스의 최대 학습 누수다.
3. **동일 항목 N라운드 연속 FAIL 시 루프 브레이커**를 걸고, (C) 의심 플래그와 함께 사람에게 넘긴다.
4. **16개 체크리스트 항목을 오류 저장소의 `subject`로 그대로 사용**한다. 클러스터링 로직이 불필요해진다.
5. **(C)와 (D)는 `destination: harness`로 직행**시킨다. 프로젝트 로컬에 남기면 §6.1에서 실측한 44% 유실이 반복된다.
6. **리뷰어 자체를 학습 대상에 포함한다.** (C)가 누적되면 리뷰어의 체크리스트나 컨텍스트를 고쳐야 한다는 신호다. 작성자만 학습하고 리뷰어는 고정된 구조는 절반만 개선된다.

### 7.8 조치 선택 게이트 — 하네스를 고칠 것인가, 데이터로 남길 것인가

귀속((A)~(D))이 정해진 다음 질문은 "그래서 무엇을 할 것인가"다. 하네스 컴포넌트를 고칠 것인가, 오류 데이터로만 남길 것인가.

#### 7.8.1 이 게이트의 관할은 (A)/(B)뿐이다

(C)와 (D)는 이미 결정되어 있다. 그리고 그 근거는 추론이 아니라 실물이다.

| 유형 | 데이터로 기록했을 때의 실제 결과 |
|---|---|
| **(C)** | `spec-review-pending-pr-dependency` — "이럴 땐 이렇게 피해 가라"는 **영구적 우회법**이 되고 리뷰어는 고쳐지지 않음 |
| **(D)** | `commit-scopes.md` 경고 **26회 반복** — 기록해도 아무것도 바뀌지 않음 |

둘 다 **하네스가 틀린 것**이지 학습해서 피할 성질이 아니다. 게이트를 태우면 오답이 나올 여지만 생긴다. (C)/(D)는 게이트를 우회해 즉시 하네스행으로 보낸다.

게이트가 실제로 필요한 영역은 (A) 작성 결함과 (B) 모호성 결함이다.

#### 7.8.2 판별 축은 "수정 vs 기록"이 아니라 "기계 검증 가능한가"

"수정할 것인가 기록할 것인가"는 **결과**를 축으로 삼는데, 결과로는 판정이 안 된다. 실제 판별 기준은 다음 한 문장이다.

> **이 규칙 위반을 코드로 판정할 수 있는가?** (파일 존재, 문자열 매칭, 스키마 검증, 명령 종료 코드)

이 축이 옳은 이유는 **양방향 실패 모드가 명확하고 각각 실증 사례가 있기 때문**이다.

| 잘못된 배치 | 결과 | 실증 |
|---|---|---|
| 기계 검증 가능한 것을 **지식으로** 주입 | 확률적으로만 지켜짐. 모델이 회상 못 하면 무효 | learned 9건 중 회상이 검증된 것 0건 |
| 판단이 필요한 것을 **하드 게이트로** 강제 | 오탐 양산 → (C) 유형 제조 | 미병합 PR 파일 체크 → NOT READY 반복 |

`commit scope가 목록에 있는가`는 스크립트 세 줄이므로 지식으로 둘 이유가 없다. 반대로 `상태 분기는 exhaustive 테이블을 먼저 정의하라`는 판단을 요구하므로 규칙 문서가 맞다 — 실제로 `state-table-before-branch`가 그렇게 승격됐다.

#### 7.8.3 이분법이 아니라 4지선다

"수정 vs 기록"으로 묶으면 성격이 다른 둘이 섞인다.

| 선택지 | 성격 | 비용 구조 |
|---|---|---|
| ① 하네스 컴포넌트 수정 (훅·게이트·체크리스트) | **동작을 바꿈** | 높은 초기 비용, 회귀 위험, 되돌리기 어려움 / 전 프로젝트 즉시 전파 |
| ② 상시 로드 규칙에 항목 추가 | **지식을 주입** (강제) | 매 세션 컨텍스트 비용 O(n) |
| ③ 조회형 오류 데이터에 기록 | **지식을 주입** (조회) | 거의 0 / 조회 실패 시 무력 |
| ④ 아무것도 안 함 | 일회성 판정 | 0 / 재발 시 손실 |

①과 ②는 둘 다 "하네스 수정"으로 묶이지만 완전히 다르다. ①은 절차를 바꾸고 ②는 컨텍스트에 문장을 넣는다.

**기본값은 ③이어야 한다.** ①은 되돌리기 어렵고 회귀 위험이 있으므로 **승격의 결과**여야지 1차 대응이면 안 된다. learned-behavior의 `candidate → approved` 구조와 같은 논리다(§5.3).

#### 7.8.4 게이트의 위치 — 회고 시점이 아니라 승격 시점

**오류가 발생한 시점에는 판정에 필요한 정보가 없다.** 이것이 반복될 문제인지 일회성인지 그때는 알 수 없는데, ①~④의 선택은 정확히 그 정보에 달려 있다.

MNL이 개별 실패가 아니라 배치 클러스터에서 학습하고(§3.1), learned-behavior가 N회 관측 + M일 경과를 승격 조건으로 두는(§5.3) 이유가 같다. **회고 시점에는 ③만 하고, 게이트는 임계값 도달 시점에 실행한다.**

|  | 기계 검증 가능 | 판단 필요 |
|---|---|---|
| **반복 임계값 미달** | ③ 데이터 기록 | ③ 데이터 기록 |
| **반복 임계값 도달** | **① 하네스 수정** | **② 규칙 승격** |

하네스 수정은 우상단 한 칸뿐이다. `commit-scopes` 건은 이 표대로면 3~4회쯤에서 ①로 갔어야 했다.

#### 7.8.5 하네스 수정 자체가 새로운 오류원이다

`spec-review-pending-pr-dependency`의 원인이 된 "Codex가 실제 파일시스템을 확인한다"는 설계는 **그 자체로는 합리적**이었다. 존재하지 않는 파일을 참조하는 스펙을 잡아내는 건 좋은 검증이다. 미병합 PR 시나리오를 놓쳤을 뿐이다.

따라서 ①을 선택할 때는 반드시 묻는다: **"이 수정이 만들어낼 새 오탐은 무엇인가."** 답하지 못하면 보류한다. MNL의 `Anti-Patterns`가 하는 역할과 같다.

#### 7.8.6 반대 논거와 비용

공정하게, 이 게이트가 불필요하다는 논거도 있다. §7.5 실측으로 지적 건수는 3개월간 80건, **월 25건 수준**이다. 게이트를 설계·운용하는 비용이 매번 사람이 판단하는 비용보다 클 수 있다.

"80건 중 처리된 게 0건"이라는 반박은 **부분적으로만 유효하다.** 그 데이터가 보여주는 것은 *강제 장치의 부재*가 실패한다는 것이지, 4문항 게이트를 월 25회 돌리는 것이 감당 가능하다는 증거는 아니다. **처리량 비용은 실재하며 본 문서는 이를 추정할 근거가 없다.**

그래서 가장 싼 형태를 권고한다 — **판정 의식이 아니라 기본값 있는 필수 필드**다.

```yaml
resolution: record   # 기본값. 다른 값을 쓰려면 근거를 적어야 함
```

기본값이 ③이므로 대부분은 판단 없이 통과하고, ①·②로 올릴 때만 비용이 발생한다. 강제성은 유지하되 처리량 비용은 최소화된다.

### 7.9 하네스 변경의 원본 반영 — 경계 · 검출 · 전파

①(하네스 수정)이 선택되었을 때, 진행 중인 프로젝트에서 직접 고치면 **원본에 전파되지 않는다.** §6.1의 44% 유실이 바로 이 현상이다.

#### 7.9.1 배포는 있고 원본 반영이 없다

cygnus 검토 결과 하네스는 **이미 배포 메커니즘을 갖고 있다.**

```json
// .harness/.deploy-manifest.json
{
  "manifest_version": 1,
  "deployed_at": "2026-07-15T00:09:34.763Z",
  "source": { "commit": "233a7fadcdbbf...", "branch": "develop" },
  "files": [ ".claude/agents/architect.md", ... ]
}
```

`deploy-manifest.js`(224줄)에 `list-src` / `read-files` / `write` / `strip-gitignore-block` 서브커맨드가 있고, `.harness-backups/harness-deploy-20260715090934/`에 배포 시 백업이 남아 있다. **원본 저장소에서 커밋 SHA를 찍어 프로젝트로 배포하는 패키지 설치 모델**이다.

문제는 둘이다.

- **단방향이다.** manifest는 "어느 커밋에서 왔는가"만 기록하고 "배포 후 무엇이 바뀌었는가"는 기록하지 않는다.
- **files[]에 해시가 없다.** 경로 목록뿐이므로 **무엇이 바뀌었는지 알 방법 자체가 없다.**

원본에 반영할 변경을 식별할 수 없다는 것이 근본 문제다. 도구가 없는 게 아니라 정보가 없다.

#### 7.9.2 gitignore가 하네스 자신의 정책을 덮었다

```
# BEGIN harness local ignores
.harness-backups/
.claude/sessions/
.claude/checkpoints.log
.claude/settings.local.json
.harness/.deploy-manifest.json
docs/_local/
# END harness local ignores
.claude          ← 관리 블록 바깥
.codex
.harness
CLAUDE.md
AGENTS.md
```

하네스가 관리하는 블록(`BEGIN`/`END` 마커, 전용 `strip-gitignore-block` 서브커맨드까지 존재)은 **세션 로그·체크포인트·로컬 설정 같은 산출물만** 무시한다. 즉 **`.claude/`와 `.harness/`는 추적되기를 기대하는 설계**다.

그런데 관리 블록 바깥의 통짜 무시가 그것을 덮었다. 결과가 **추적 파일 0건, 커밋 이력 없음, 수동 백업 1건**이다.

**이것이 44% 유실의 기계적 원인이다.** 학습이 하네스 레벨이어도 그 파일이 버전관리 밖에 있으면 diff도 없고 원본에 반영할 커밋도 없다. 판단의 문제가 아니라 인프라의 문제였다.

#### 7.9.3 해결 순서 — 전파를 먼저 고르면 안 된다

순서는 **경계 → 검출 → 전파**다. 이유는 **전부 원본에 반영하면 안 되기 때문**이다. `commit-scopes.md`를 원본에 반영하면 특정 프로젝트의 스코프가 원본을 오염시킨다. 경계 없이 전파 경로를 만들면 프로젝트 특수성이 상류로 흘러간다.

**1단계 — 경계를 물리적으로 만든다.** `commit-scopes.md`가 (D) 사고를 낸 근본 원인은 **프로젝트 설정 파일이 하네스 디렉터리 안에 있다는 것**이다. `.harness/README.md`가 "프로젝트별 파일이다"라고 선언하면서 위치는 `.harness/` 안에 두었다. 선언과 배치가 어긋났다.

| 계층 | 소유 | 배포 시 | 원본 반영 |
|---|---|---|---|
| `core/` | 원본 하네스 | 덮어씀 | **편집 = 원본 반영 대상** |
| `config/` | 프로젝트 | 없으면 템플릿에서 생성, 있으면 보존 | 없음 |
| `local/` | 이 프로젝트 전용 | 건드리지 않음 | 없음 |

이 분리는 **"이 변경이 하네스행인가"를 판단에서 경로 조회로 바꾼다.** 그리고 §7.8의 게이트에서 (D) 유형이 구조적으로 사라진다 — `config/` 파일은 애초에 원본 기준으로 검증되지 않기 때문이다.

**2단계 — 드리프트를 검출 가능하게 만든다.** manifest에 파일별 해시를 추가한다.

```json
"files": [ { "path": ".claude/skills/flow-impl/SKILL.md", "sha256": "..." } ]
```

`현재 해시 vs 배포 시 해시` 비교로 "이 프로젝트에서 core의 무엇이 바뀌었는가"가 정확히 산출된다. 비용은 필드 하나와 비교 커맨드 하나다. 동시에 gitignore의 통짜 무시를 걷어내 관리 블록만 남긴다(비용 거의 0).

**3단계 — 전파 경로.** 두 전략은 근본적으로 다르다.

| | (a) 공유 체크아웃 + 심볼릭 링크 | (b) 배포 + 드리프트 강제 |
|---|---|---|
| 전략 | 원본 반영을 **불필요**하게 만듦 | 원본 반영을 **검출 가능**하게 만듦 |
| core 편집 위치 | 원본 저장소 그 자체 | 프로젝트 사본 |
| 격리 | **없음** — A를 위한 수정이 즉시 B에 적용, 깨진 중간 상태도 전파 | 있음 |
| 버전 고정 | 불가 (worktree 사용 시 가능하나 복잡) | 가능 (커밋 SHA 핀) |
| 실패 모드 | 실험이 다른 프로젝트를 깨뜨림 | **원본 반영 명령을 안 돌리면 유실** |
| 기존 자산 | 배포 메커니즘 폐기 | manifest·backup·script 재사용 |

(a)는 문제를 **구조적으로 소멸**시킨다. core를 심볼릭 링크로 걸면 프로젝트에서 편집하는 순간 그것이 원본 편집이므로 원본 반영이라는 개념이 없어진다. 대가는 격리 상실이다.

(b)는 기존 구조를 유지하지만 **원본 반영이 여전히 명시적 행위**다. cygnus 데이터가 보여주듯 명시적 행위는 실행되지 않는다(§2.3). 따라서 (b)를 고르면 **강제 지점이 필수**이며, 그 지점은 §7.8.4와 동일하다 — `/flow-pr` 또는 `/flow-done`에서 core 드리프트가 감지되면 차단한다.

**절충안**: `core/`만 읽기 전용 심볼릭 링크, `config/`·`local/`은 실파일. core 편집이 물리적으로 불가능해지므로 원본 반영 문제가 사라지면서 프로젝트별 설정은 격리된다. 대가는 버전 고정 포기다.

#### 7.9.4 권고 — 1·2단계를 먼저, 3단계는 미룬다

경계 분리와 해시 기반 드리프트 검출은 어떤 전파 전략을 고르든 필요하다. 그리고 이 둘만으로 **"무엇이 유실되고 있는지"가 보이기 시작한다.** 현재는 그것조차 보이지 않는다.

3단계 선택 기준은 명확하다 — **동시에 운용하는 프로젝트 수**다. 하나면 (a)의 격리 상실이 비용이 아니고, 둘 이상이면 (b)가 맞다.

> **후속 조사 (2026-08-02): [harness-distribution.md](harness-distribution.md)** — 이 절의 (a)/(b) 이분법 바깥에 제3의 형태가 존재함이 확인됐고, 경계와 검출을 배포 메커니즘 안에 포함하는 선택지가 있어 "3단계는 미룬다"의 근거가 약해졌다. §7.9.1의 "해시 없어 드리프트 검출 불가"에 대한 권고 #17도 그 문서 §2.2·§7에서 정정됐다. 메커니즘 선택은 아직 확정하지 않았다.

### 7.10 이슈 기반 리포팅 — 지식을 원본에 반영하는 유일한 경로

#### 7.10.1 코드 반영과 지식 반영은 다른 문제다

원본 반영는 사실 두 개다.

1. **코드 원본 반영** — 변경된 파일이 원본에 도달하는 것
2. **지식의 원본 반영** — *수정이 필요하다는 사실*이 원본에 도달하는 것

원본 저장소의 이슈 시스템은 2번만 해결한다. 그런데 **가장 중요한 두 유형에서는 애초에 1번이 성립하지 않는다.**

| 유형 | 실증 | diff 상태 |
|---|---|---|
| **(D)** `commit-scopes.md` | 올바른 조치는 프로젝트 스코프로 교체 — **원본 반영 금지 대상**. 원본이 알아야 할 것은 "배포 시 config가 교체되지 않으면 오탐이 난다"는 **배포 절차의 결함** | 원본에 반영하면 오염 |
| **(C)** 미병합 PR | 프로젝트는 하네스 파일을 **건드리지 않았다.** 우회법을 learned 스킬로 저장했을 뿐 | **존재하지 않음** |

두 사례 모두 파일 diff로는 정보를 옮길 수 없다. **이슈만이 가능하다.** 이는 이슈 방식을 보완재가 아니라 (C)/(D)의 **유일한 경로**로 만든다.

#### 7.10.2 더 강한 논거 — 임계값 문제가 여기서 풀린다

§7.8.4의 반복 임계값은 근거를 대기 어려웠다. 근본 이유는 **한 프로젝트 안에서는 표본이 모자라기 때문**이다. 월 25건 규모에서 같은 결함이 3회 반복되기까지 오래 걸린다.

**이슈는 원본 저장소에 모인다.** 여러 프로젝트에서 올라온 같은 결함이 자동으로 한곳에 쌓이므로, **이슈 저장소가 곧 교차 프로젝트 반복성 측정 장치**가 된다. 라벨별 이슈 수가 그대로 승격 신호다.

이는 (C)/(D) 논거보다 구조적으로 더 큰 이점이다.

#### 7.10.3 이슈와 파일 반영의 관계

이슈가 파일 원본 반영을 대체하지 않는다. **이슈가 먼저이고 파일 반영은 해소 수단 중 하나다.**

```
드리프트·귀속 검출 (§7.3, §7.9.2)
        ↓
   이슈 (원본 저장소)
        ↓
    [해소 수단]
        ├─ 원본에서 파일 직접 수정          (A)/(B)
        ├─ 배포 스크립트에 config 계층 처리   (D)
        ├─ 리뷰어 프롬프트·체크리스트 수정    (C)
        └─ wontfix — 프로젝트 특수성으로 판정
```

(D)가 명확한 예다. 이슈는 *"배포 시 config 파일이 교체되지 않는다"*이고, 해소는 `commit-scopes.md`의 내용 수정이 아니라 **배포 스크립트에 config 계층 개념을 추가하는 것**이다. 파일 diff를 따라가서는 도달할 수 없는 해법이다.

#### 7.10.4 인프라 비용은 0이다

cygnus는 `git@github.com:smalljiny/cygnus.git`를 원격으로 쓰고, `/flow-pr`이 이미 `gh pr create` / `gh pr edit` / `gh auth status`를 호출한다. `/flow-setup git`이 원격을 자동 감지해 `config.git.*`에 저장한다. `gh issue create` 추가에 새로 붙일 인프라가 없다.

#### 7.10.5 성패를 가르는 지점 — 생성의 강제

유일하게 중요한 설계 결정이다. cygnus 데이터가 답을 이미 줬다 — **명시적 행위로 두면 실행되지 않는다**(학습 루프 2.5개월 정지, 지적 80건 중 처리 0건).

`gh issue create`는 스크립트 호출이 가능하므로 강제 지점에 박을 수 있고, 그 지점은 §7.8.4·§7.9.3과 동일하다.

> `/flow-pr` 또는 `/flow-done`에서 core 드리프트가 있거나 (C)/(D) 귀속 항목이 있으면, **이슈가 생성되었거나 기존 이슈에 링크되어야 통과**한다.

#### 7.10.6 실질적 리스크 — 두 번째 방치 큐

가장 큰 위험이다. 이슈함이 `learned/`처럼 정지된 또 하나의 큐가 될 수 있다. 완화책 셋:

1. **템플릿 강제** — 자동 생성 시 귀속 유형, 발생 프로젝트, 반복 횟수, 리뷰 파일 경로, 관련 커밋을 실어 보낸다. 쓰는 시점에는 맥락이 있고 읽는 시점에는 없기 때문이다.
2. **미해결 이슈 수를 감사 지표로** — §2.3에서 지적한 "파일 존재 여부만 채점"의 실질적 개선이 된다. 파일이 있는지가 아니라 백로그가 쌓이는지를 본다.
3. **라벨별 임계값 알림** — 같은 라벨 이슈가 N개를 넘으면 그것이 승격 신호다.

#### 7.10.7 대안 비교 — 로컬 파일로는 안 되는 이유

| | 로컬 파일 (`docs/harness-backlog.md`) | 원격 이슈 |
|---|---|---|
| 의존성 | 없음 | GitHub (이미 사용 중) |
| 속도 | 빠름 | API 왕복 |
| **교차 프로젝트 집계** | **불가** | 자동 |
| 중복 탐지 | grep | 검색 API (정확도 미확인) |
| 상태 추적 | 수동 | open / closed |

결정타는 **교차 프로젝트 집계**다. 파일 방식이면 그 파일의 위치가 문제가 된다 — 원본 저장소에 두면 프로젝트에서 쓰려고 클론해야 하고 결국 원격 접근이 필요해진다. **요구사항(교차 프로젝트 반복성 측정)이 원격 저장소를 강제한다.**

#### 7.10.8 미해결 사항

- **해소는 강제할 수 없다.** 생성은 게이트로 강제 가능하지만, 이슈를 읽고 처리하는 것은 규율의 문제다.
- **자동 생성 이슈의 품질**은 실측이 필요하다. 템플릿이 좋아도 본문이 부실하면 나중에 판단할 수 없다.
- **중복 억제가 미해결**이다. §5.4의 "쓰기 전 조회 → 병합 우선" 원칙이 여기도 필요한데, 이슈에서 병합은 코멘트 추가가 된다. GitHub 검색으로 유사 이슈를 찾는 정확도는 미확인.
- **정보 유출 주의.** 이슈 본문에 프로젝트 코드·경로·도메인 용어가 실려 원본 저장소로 간다. 원본이 공개 저장소라면 komi-learn식 결정론적 사전 필터(§6.2)가 필요하다.

## 8. 인접 분야 — SRE 포스트모템

에이전트 이전에 사람이 같은 문제를 30년간 풀어왔다. 세 가지가 직접 적용된다.

**무비난(blameless) 원칙.** Google SRE 워크북은 "인적 오류는 조사의 **결론이 아니라 출발점**"이라고 규정한다. 에이전트 회고에 대입하면: "모델이 실수했다"에서 멈추지 말고 **하네스의 어떤 조건이 그 실수를 허용했는가**까지 내려가야 한다. 이것이 곧 축 4의 `destination: harness` 판정으로 이어진다.

**액션 아이템에 담당자와 기한.** 포스트모템의 실질은 문서가 아니라 **추적되는 액션 아이템**이다. 재발 방지가 실제로 이뤄지는 지점이 여기다. cygnus의 `wf-agent-debug`에는 `Preventive change to encode later:`라는 필드가 있으나 **이를 소비하는 곳이 없다.** 액션 아이템을 만들되 추적하지 않는 전형적 실패다.

**자동 타임라인 수집.** 사후에 기억으로 재구성하지 말고 발생 시점에 자동 기록한다. 훅 기반 세션 로깅이 이에 해당하며, cygnus에도 이미 있다(`session-logger`). 문제는 기록이 아니라 그것을 읽는 단계가 파이프라인에 없다는 것이었다.

### 9.4 열린 질문 — 후속 조사 필요

1. **스펙 단계 오류 검출** — *부분적으로 해소됨.* 독립 리뷰어 구조(§7)와 사람/AI 결정 태깅(§2.2) 두 가지가 확인됐다. 다만 본 조사의 9개 질의는 이 축을 직접 겨냥하지 않았으므로, 요구공학 문헌(스펙 모호성 자동 검출, 결정 로그, 명세 일관성 검증)은 여전히 미조사 영역이다.
2. **(B)와 (C)의 자동 구분.** §7.3은 "표현만 변경 vs 내용 변경"으로 (A)/(B)를 가르는데, 이 판정을 diff에서 기계적으로 내리는 방법이 불분명하다. 의미 보존 여부를 판정해야 한다.
3. **(D) 판별 임계값.** "여러 토픽에서 반복"의 기준을 몇 회로 잡을지. 실측에서는 26회까지 갔지만, 3회쯤에서 잡았어야 했다.
4. **`destination` 자동 판정.** 하네스 결함인지 기술 일반 지식인지를 사람이 매번 판정하면 부담이 크다. 자동 분류 휴리스틱이 필요하다. (C)/(D)는 §7.3이 자동 판정하므로 나머지 경우만 해당한다.
5. **하네스 개선 백로그의 소비.** `destination: harness` 항목이 쌓였을 때 grid fin 저장소에 실제로 반영하는 워크플로우 — 사람이 언제 어떻게 처리하는가.
6. **승격 임계값의 초기값.** 개인 사용에서는 관측 빈도가 낮아 팀 규모 기준(N회/M일)이 그대로 맞지 않는다.
7. **리뷰어 자체의 학습.** (C)가 누적되면 리뷰어를 고쳐야 하는데, 리뷰어(Codex)는 별도 프로세스이고 별도 스킬 체계를 갖는다. 작성자 학습과 리뷰어 학습을 어떻게 분리해서 관리할 것인가.
8. **게이트의 처리량 비용.** §7.8.6 — 월 25건 규모에서 조치 선택 게이트를 돌리는 비용을 추정할 근거가 없다. 기본값 방식으로 최소화했으나 실측이 필요하다.
9. **`core`와 `config`의 경계.** §7.9.3 — `commit-scopes.md`는 명백히 config이지만, 리뷰 체크리스트 16항목은 애매하다. 프로젝트마다 검증 항목이 달라야 할 수도 있다.
10. **3계층 분리의 소급 적용 비용.** grid fin은 처음부터 설계하면 되지만, 기존 하네스에 적용하려면 파일 이동과 모든 경로 참조 수정이 필요하다. 비용을 추정할 근거가 없다.
11. **이슈 중복 억제.** §7.10.8 — GitHub 검색으로 유사 이슈를 찾아 링크하는 정확도가 미확인이다.
12. **원본 반영의 정확성 판정.** 드리프트가 검출되어도 그 변경이 원본에 맞는지(다른 프로젝트를 깨지 않는지)는 자동으로 알 수 없다. 개인 하네스에는 원본 테스트가 없을 가능성이 높아 더 그렇다.

## 부록 A. 조사 방법 및 한계

**방법**: Exa `/search`(type: auto, 콘텐츠 텍스트·요약·하이라이트 포함) 9회 질의, Firecrawl `/v1/scrape` 2회. 질의 축은 ① 실패 메모리·근본 원인 저장, ② 자기개선 코딩 에이전트, ③ 경험 학습(ExpeL 계열), ④ 컨텍스트 진화(ACE), ⑤ 감쇠·망각·승격, ⑥ 예방적 조회, ⑦ SRE 포스트모템, ⑧ 절차 메모리(AWM), ⑨ 프로젝트 횡단 지식 공유.

**2026-08-02 재구성**: 외부 자료를 「구현 참조 자료」 절로 앞당겨 모았다. **절 번호는 바꾸지 않았다** — 조사 문서 8건이 서로를 §번호로 참조하고 있어 재번호는 그 링크 그래프를 조용히 깨뜨린다. 재구성은 읽는 순서와 찾기 쉬움에 대한 것이지 번호에 대한 것이 아니다.

**§7 전체가 문헌 조사가 아니다.** cygnus 저장소를 직접 읽어 얻은 1차 관측이다.

- **§7.1~7.6** — `docs/_local/**`의 **실제 리뷰 산출물 55건** 집계. Decision 분포, 체크리스트 항목별 FAIL/NOTE 빈도, 반복 NOTE의 내용, `.harness/commit-scopes.md`의 실재 내용과 mtime을 모두 파일에서 확인.
- **§7.8** — 문헌(MNL·learned-behavior)의 원칙을 위 실측에 적용한 **설계 제안**이다. 검증된 설계가 아니다.
- **§7.9** — `.deploy-manifest.json`, `deploy-manifest.js`, `.harness-backups/`, `.gitignore`를 직접 읽어 확인. 3계층 분리와 전파 전략 비교는 **제안**이다.
- **§7.10** — `gh` 사용 실적과 원격 설정은 확인된 사실. 이슈 기반 리포팅의 효과는 **미검증 제안**이다.

**표본 한계**: §7.1~7.6의 수치는 **단일 프로젝트·단일 사용자** 표본이다. 도출된 비율(예: NOTE가 FAIL의 2배 이상)이 일반적이라고 볼 근거는 없으며 grid fin에서 재측정이 필요하다. 다만 (C)/(D) 유형의 **존재** 자체는 표본 크기와 무관하게 성립한다 — 각각 실물 증거가 하나씩 있다.

- 논문은 초록·서론 및 검색 엔진이 제공한 본문 일부에 근거했다. 실험 설정과 재현 조건까지 검증하지 않았다. 인용한 수치는 **저자 주장치**다.
