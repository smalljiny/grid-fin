## 구현 참조 자료 — 외부 자료 정리

> **이 절의 쓰임.** 이 조사가 확인한 외부 자료를 **구현 시 참조할 형태**로 모았다. 논증과 검증 상태는 괄호 안 절 번호에 있다.

### A. 도구가 이미 인정하고 대응한 것 — Claude Code

**이 주제에서 가장 신뢰도 높은 근거다** — 도구 제작자가 문제를 인정하고 기능을 넣은 기록 (§2, changelog 확인).

| 기능 | 무엇을 규정하는가 |
|---|---|
| **`/doctor`의 CLAUDE.md 검사** | *"proposes trimming checked-in CLAUDE.md files by **cutting content Claude could derive from the codebase**"* — **제외 기준이 명시되어 있다** (포함 기준은 아니다) |
| **스킬 description 상한** | 250자 → **1,536자**로 상향, 초과 시 시작 시 경고. **개별 항목에만 걸리고 총합에는 걸리지 않는다** |
| **`/context all`** | 모델 토크나이저 기준 **스킬별 토큰 추정치**. 컨텍스트 과다 도구·메모리 비대·용량 경고를 지목 |
| **MEMORY.md 인덱스 예산** | 초과 시 **조용한 잘림이 아니라 명시적 오류**. 측정 대상에서 frontmatter·HTML 주석 제외 — **"로드되는 것만 센다"** |
| **훅 출력 50K 상한** | 초과분은 디스크 저장 + 경로·미리보기만 주입 |
| **`PreCompact` 훅** | exit 2 또는 `{"decision":"block"}`으로 **압축을 차단** |

**예산 메커니즘의 참고 사례가 둘 있다** — 하드 실패(조용한 잘림 금지)와 로드되는 것만 계산.

### B. 위치 효과 — Lost in the Middle (피어리뷰)

[Liu et al., 2023](https://cs.stanford.edu/~nfliu/papers/lost-in-the-middle.arxiv2023.pdf) (§3.1). 다문서 QA·key-value 검색에서 **성능이 정보 위치의 U자 함수**를 따른다. 처음이나 끝에 있을 때 정확도가 가장 높고 **중간이면 30% 이상 하락**한다.

### C. 열화의 형태 — 절벽이지 선형이 아니다

18개 프런티어 모델 측정 보고 (§3.2, **검색 요약 근거**). 입력이 길어질수록 정확도가 **비균일하게** 하락하며 **문서상 한계 훨씬 전에 30~50% 떨어지기도** 한다. 어떤 모델은 32K에서 멀쩡하다 64K에서 무너지고 어떤 모델은 훨씬 뒤까지 버틴다.

**권고 측정법**: 16K/32K/64K/128K/256K에서 정확도를 재고 **허용 최대치의 20% 아래에서 운용**.

> **함의가 구현 지침이다** — 절벽 위치가 모델마다 다르므로 **예산은 측정으로 정하는 값이지 상수가 아니다.**

### D. 무엇을 넣을 것인가 — ETH Zurich

[Gloaguen, Mündler, Müller, Raychev, Vechev, *Evaluating AGENTS.md* (arXiv 2602.11988)](https://arxiv.org/abs/2602.11988) (§6.1, 초록 확인).

> *"providing context files does not generally improve task success rates, while **increasing inference cost by over 20% on average**"* — **LLM 생성과 개발자 작성 양쪽 모두**
> ***"instructions in the context files are well followed by coding agents, repository overviews, although popular and recommended by model providers, are not helpful"***
> *"context files are useful for specifying **non-standard coding practices**"*

**조절 변수가 길이가 아니라 내용 종류다.** 이 결론은 A의 `/doctor` 기준("코드에서 유도 가능한 것은 빼라")과 독립적으로 같은 경계를 그리지만, **"사람이 다듬으면 낫다"는 처방은 반박한다.**

### E. 압축이 제약을 지운다 — Governance Decay

[arXiv 2606.22528](https://arxiv.org/abs/2606.22528) (§4.1, 초록 확인). ConstraintRot 벤치마크, 7개 모델 계열, **1,323 에피소드**.

| 조건 | 정책 위반율 |
|---|---:|
| 정책이 완전히 보이는 상태 | **0%** |
| 압축 후 (전체) | 최대 **59%**, 평균 **30%** |
| 압축에서 제약이 **생존** | **0%** |
| 압축에서 제약이 **제거** | **38%** |

**메커니즘 분해가 깨끗하다** — 위반은 압축 자체가 아니라 *제약의 소실*에서 온다. 제안 완화책은 **Constraint Pinning**(훈련 없이 거버넌스 제약을 손실성 압축에서 격리).

**A의 `PreCompact` 차단 지점과 짝이 되지만 둘을 연결한 자료를 찾지 못했다**(§7-1).

### F. 압축의 대안 셋

| 전략 | 방식 | 대표 |
|---|---|---|
| 압축(compaction) | LLM이 대화를 요약해 원본을 대체 | Claude Code `/compact` |
| **eviction** | 의미 인식 기반으로 **결정론적** 제거 | [CWL (arXiv 2606.11213)](https://arxiv.org/abs/2606.11213) |
| 핸드오프 | 정해진 스키마로 상태를 이관 | 실무 관행 |

CWL은 작업을 타입 지정된 의존성 연결 에피소드로 주석하고, 예산 초과 시 결정론적 정책이 우선순위대로 제거하되 **사용자 입력과 활발한 추론 맥락은 보존**한다. 요약 기반 압축의 한계로 넷을 든다 — 예측 불가한 정보 손실, 인과 구조 파괴, 모델 비용, **압축 유도 환각**.

[SelfCompact (arXiv 2606.23525)](https://arxiv.org/abs/2606.23525)는 *언제* 압축할지를 규칙화 — **작은 과제 완료·궤적 수렴 시 실행, 중간 단계·교착 시 억제**. 질문당 비용 30~70% 감소 보고.

> **세 전략 모두 하네스 규칙의 생존을 명시적으로 다루지 않는다** — E가 그것이 결정 요인임을 보였는데도.

### G. 지시 준수는 별개 축이다

[The Compliance Gap (arXiv 2605.01771)](https://arxiv.org/pdf/2605.01771) (§3.3, **PDF 추출 부분적**). 준수율이 떨어지는 조건 셋 — 과제 복잡성 증가, 인지 부담, **동시에 지켜야 할 제약이 많을 때**.

그리고 구조적으로 중요한 지적 하나 — 모델에는 *"이것은 사용자 지시이므로 반드시 지켜야 한다"* 와 *"이것은 40분 전 grep 출력이므로 무시해도 된다"* 를 구분하는 내부 장치가 없다. **위치만으로는 해결되지 않는다.**

### 1.2 아무도 세지 않는 층 — 라우팅 표면

스킬은 온디맨드로 로드되지만 **description은 목록으로 상시 제시된다.**

| 항목 | 값 |
|---|---:|
| 최상위 스킬 디렉터리 | 47 |
| `SKILL.md` 총 개수 | 55 |
| frontmatter `description` 합계 | **10,185자** |
| 평균 description 길이 | 185자 |
| 온디맨드 본문 합계 | 12,606줄 / 421,363바이트 |

**description 합계 10,185자는 상시 로드 계층(41,900바이트) 대비 약 24%다.** 그런데 이 층은 하네스 어디에서도 예산으로 관리되지 않는다.

중첩 구조 주의 — 55개 중 8개가 `learned/` 아래 한 단계 더 깊이 있다. 이들이 세션 목록에 실제로 노출되는지는 확인하지 않았다.

> **측정의 성격**: 위 수치는 **파일 내용을 잰 것**이지 세션 컨텍스트 비용을 잰 것이 아니다. 스코프(user/project/plugin)에 따라 실제 목록에 오르는 스킬 집합이 달라진다. 실제 비용은 §2.3의 도구로 재야 한다.

### 1.3 강제와 권고가 구분되지 않는다

규칙 파일별 마커 개수. 강제형 = `MUST|NEVER|ALWAYS|절대|금지|반드시|해야 한다|하지 않는다|**볼드`, 권고형 = `권장|선호|가급적|prefer|should`.

| 파일 | 강제형 | 권고형 |
|---|---:|---:|
| `coding-style.md` | **0** | 0 |
| `git-workflow.md` | 12 | 1 |
| `security.md` | 6 | 0 |
| `testing.md` | 2 | 1 |
| `typescript/patterns.md` | **0** | 0 |
| `typescript/testing.md` | **0** | 2 |

**6개 중 3개가 강제형 마커 0이다.** 그리고 권고형 마커는 전 파일에서 거의 없다.

정확히 말하면 "우선순위 구분이 없다"가 아니라 **"명시적 우선순위 마커의 사용이 파일마다 불균일하다"**이다. 문장 자체가 강제인지 권고인지는 읽어야 알 수 있다. 이는 §6.1이 지목하는 "우선순위 혼재" 문제의 국소 사례다.

### 1.4 하네스는 자기 크기를 재지 않는다

`.claude/scripts/harness-audit.js`를 검사한 결과, 파일 크기·줄 수·컨텍스트 예산에 해당하는 검사 항목이 없다. 감사 도구는 존재하나 **상시 로드 계층의 비대화는 감사 대상이 아니다.**

이는 선행 조사가 지적한 패턴과 같다 — [오류 재발 방지 조사 §2.3](error-recurrence-prevention.md)이 "파일 존재 여부만 채점"을 지적했다. 크기 역시 채점되지 않는다.

## 2. 도구가 이미 인정한 것

Claude Code changelog는 이 주제에서 **가장 신뢰도 높은 문헌 근거**다. 도구 제작자가 문제를 인정하고 대응 기능을 넣은 기록이기 때문이다.

### 2.1 CLAUDE.md 비대화는 공식 인정된 문제다

> "Added a `/doctor` check that proposes trimming checked-in `CLAUDE.md` files by cutting content Claude could derive from the codebase"

**판단 기준이 명시되어 있다 — "Claude가 코드베이스에서 유도할 수 있는 내용"은 빼라.** 이는 여러 실무 자료가 제시하는 기준과 같고, 여기서는 1차 근거로 확인된다.

즉 아젠다 §1의 조사 질문 중 **"상시/온디맨드 경계를 무엇으로 가르는가"에 대한 답의 한 축이 도구 쪽에서 이미 제시되어 있다.** 다만 이는 *제외 기준*이지 *포함 기준*이 아니다.

### 2.2 라우팅 표면에는 이미 상한이 있다

시간 순으로:

> "Skill descriptions in the `/skills` listing are now capped at 250 characters to reduce context usage"

이후:

> "Improved skill description handling: raised the listing cap from 250 to 1,536 characters and added a startup warning when descriptions are truncated"

**현재 상한 1,536자, 초과 시 시작 시 경고.** 관측된 하네스의 평균 description은 185자로 상한의 12% 수준이라 잘림은 없다(§1.2).

여기서 나오는 함의: **상한이 개별 description에 걸려 있지 총합에는 걸려 있지 않다.** 스킬 47개면 이론상 최대 72KB까지 라우팅 표면이 커질 수 있다. 실제 하네스는 10KB지만, 스킬이 늘어날 때 총합을 제어하는 장치는 없다.

관련 기록:

> "Changed hook output over 50K characters to be saved to disk with a file path + preview instead of being injected directly into context"

훅 출력에도 컨텍스트 보호 장치가 들어갔다.

### 2.3 측정 도구가 이미 있다

> "`/context all` per-skill token estimates now account for the model's tokenizer and show rounded values"

> "Added actionable suggestions to `/context` command — identifies context-heavy tools, memory bloat, and capacity warnings with specific optimization tips"

**스킬별 토큰 추정을 모델 토크나이저 기준으로 제공한다.** §1의 바이트 측정을 토큰으로 환산할 필요 없이 직접 잴 수 있다.

### 2.4 메모리 인덱스에는 강제 예산이 있다

> "Memory writes that leave a MEMORY.md index over its read limit now produce an explicit error instead of silent truncation"

> "Improved the memory index over-limit warning to measure only loaded content, excluding frontmatter and HTML comments"

**초과 시 조용한 잘림이 아니라 명시적 오류다.** 그리고 측정 대상에서 frontmatter와 HTML 주석을 제외한다 — "로드되는 내용만 센다"는 원칙이 구현되어 있다.

이 두 가지(하드 실패 + 로드되는 것만 계산)는 예산 메커니즘의 참고 사례가 된다.

## 3. 열화의 근거

### 3.1 Lost in the Middle (피어리뷰)

[Liu et al., 2023](https://cs.stanford.edu/~nfliu/papers/lost-in-the-middle.arxiv2023.pdf)

- 다문서 QA와 key-value 검색에서 **성능이 정보 위치의 U자 함수**를 따른다
- 관련 정보가 **처음이나 끝**에 있을 때 정확도가 가장 높다
- 중간에 있으면 **30% 이상 하락**

**함의**: 1,044줄 상시 로드 계층에서 중간 위치의 규칙은 구조적으로 불리하다. `harness-guide.md`가 377줄이므로, 그 안쪽 규칙과 그 뒤에 이어지는 `rules/*.md` 앞부분이 정확히 중간 구간이다.

### 3.2 열화는 절벽 형태다

18개 프런티어 모델(GPT-4.1, Claude 4 계열, Gemini 2.5, Qwen3) 측정 보고:

- 입력이 길어질수록 정확도가 **비균일하게** 하락하며, **문서상 한계 훨씬 전에 30~50% 떨어지기도 한다**
- 선형 열화가 아니라 **절벽**이다 — 어떤 모델은 32K에서 멀쩡하다가 64K에서 무너지고, 어떤 모델은 훨씬 뒤까지 버티다 갑자기 무너진다

권고되는 측정법: 16K/32K/64K/128K/256K에서 정확도를 재고, 허용 가능한 최대 크기를 안전 예산으로 잡되 **그 20% 아래에서 운용**한다.

**함의**: "몇 줄까지 괜찮은가"라는 질문에 모델 독립적 답이 없다. 절벽 위치가 모델마다 다르므로 **예산은 측정으로 정해야 하는 값이지 상수가 아니다.**

### 3.3 지시 준수는 별개의 문제다

[The Compliance Gap (arXiv 2605.01771)](https://arxiv.org/pdf/2605.01771) — BS-Bench로 프로세스 지시 준수를 측정. 준수율이 떨어지는 조건으로 셋을 든다: 과제 복잡성 증가, 인지 부담, **동시에 지켜야 할 제약이 많을 때**.

그리고 검색 결과에서 나온 지적 하나가 구조적으로 중요하다.

> 모델에는 "이것은 사용자 지시이므로 반드시 지켜야 한다"와 "이것은 40분 전 grep 출력이므로 무시해도 된다"를 구분하는 내부 장치가 없다.

**즉 지시가 컨텍스트 앞쪽에 있어도, 의미가 비슷하거나 더 빈번한 토큰에 묻힐 수 있다.** 위치만으로는 해결되지 않는다.

## 4. 압축이 규칙을 지운다

### 4.1 Governance Decay

[arXiv 2606.22528](https://arxiv.org/abs/2606.22528). 컨텍스트 압축이 안전 제약을 제거하는 실패 모드를 명명하고 측정했다.

**실험**: ConstraintRot 벤치마크, 7개 모델 계열, **1,323 에피소드**.

| 조건 | 정책 위반율 |
|---|---:|
| 정책이 완전히 보이는 상태 | **0%** |
| 압축 후 (전체) | 최대 **59%**, 평균 **30%** |
| 압축에서 제약이 **생존**한 경우 | **0%** |
| 압축에서 제약이 **제거**된 경우 | **38%** |

**메커니즘 분해가 깨끗하다** — 위반은 압축 자체가 아니라 *제약의 소실*에서 온다. 살아남으면 0%다.

논문이 제안하는 완화책은 **Constraint Pinning** — 훈련 없이 거버넌스 제약을 손실성 압축에서 격리해 위반을 0%로 복구한다고 주장한다.

> 2026 arXiv 프리프린트이며 피어리뷰 전이다. 다만 실험 규모(7개 계열 × 1,323 에피소드)와 메커니즘 분해가 이 조사에서 본 2026 프리프린트 중 가장 단단하다.

### 4.2 도구에 차단 지점이 이미 있다

changelog:

> "Added PreCompact hook support: hooks can now block compaction by exiting with code 2 or returning `{"decision":"block"}`"

**압축을 차단할 수 있는 훅 지점이 존재한다.** 그리고 기존 하네스는 이미 훅 체계를 갖고 있다.

§4.1과 §4.2는 각각 독립적으로 확인된 사실이고, **둘을 연결한 자료는 찾지 못했다.** 여기서 이 조사의 가장 날카로운 열린 질문이 나온다(§7).

### 4.3 압축·eviction·핸드오프

세 전략이 경쟁 중이다.

| 전략 | 방식 | 대표 |
|---|---|---|
| 압축(compaction) | LLM이 대화를 요약해 원본을 대체 | Claude Code `/compact` |
| eviction | 의미 인식 기반으로 복구 가능한 오래된 내용을 결정론적으로 제거 | [CWL (arXiv 2606.11213)](https://arxiv.org/abs/2606.11213) |
| 핸드오프 | 정해진 스키마로 상태를 뽑아 새 세션에 이관 | 실무 관행 |

**Beyond Compaction**이 요약 기반 압축의 한계로 넷을 든다 — 예측 불가한 정보 손실, 인과 구조 파괴, 모델 비용 발생, **압축 유도 환각**. CWL은 작업을 타입이 지정된 의존성 연결 에피소드로 주석하고, 예산 초과 시 결정론적 정책이 우선순위대로 제거한다. 사용자 입력과 활발한 추론 맥락은 보존한다. 단일 세션이 8천만 토큰에 걸쳐 89개 순차 작업을 "측정 가능한 정확도 저하 없이" 완료했다고 보고한다.

**SelfCompact** ([arXiv 2606.23525](https://arxiv.org/abs/2606.23525))는 고정 간격 압축 대신 *언제 압축할지*를 규칙으로 정한다 — 작은 과제 완료·궤적 수렴 시 실행, 중간 단계·교착 상태에서 억제. 6개 벤치마크 7개 모델에서 고정 간격 대비 동등 이상 성능을 토큰 비용의 일부로 달성했고, 질문당 비용 30~70% 감소를 보고한다.

**세 전략 모두 하네스 규칙의 생존을 명시적으로 다루지 않는다.** §4.1이 그것이 결정 요인임을 보였는데도 그렇다.

## 5. 계층 분리에 관한 규정

> **이하 §5·§6의 형식 규정과 수치는 전부 자가출판 단일 출처**([Learn Harness Engineering](https://walkinglabs.github.io/learn-harness-engineering/en/)) **에서 나왔다.** 방법론·표본 설명이 없고 독립 재현을 찾지 못했다. 구조적 주장은 §3·§4의 검증된 근거와 방향이 일치하지만, **수치는 판단 근거로 쓰면 안 된다.**

### 5.1 단일 거대 파일이 실패하는 이유 (강의 4)

출처가 제시하는 악순환 — 에이전트 오류 발생 → 규칙 추가로 대응 → 파일 비대화 → 성능 악화 → 오류 증가.

네 가지 문제로 나눈다.

| # | 문제 | 이 조사의 검증 상태 |
|---|---|---|
| 1 | 컨텍스트 예산 낭비 (600줄 ≈ 10~20K 토큰 = 128K의 8~15%) | 방향은 §3.2와 일치, 수치 미검증 |
| 2 | 중간 정보 손실 | **§3.1로 독립 확인됨** (Liu et al. 인용) |
| 3 | 우선순위 혼재 — 하드 제약과 가이드라인과 사실 기록이 같은 형식 | **§1.3으로 국소 확인됨** |
| 4 | 유지보수 부실 — 추가는 쉽고 삭제는 어렵다 | §1.4와 일치 (감사 없음) |

**3번이 특히 구체적이다** — 출처의 예시는 `eval() 절대 금지`(하드 제약), `함수형 선호`(가이드라인), `WebSocket 메모리 누수 수정함`(사실 기록)이 같은 형식으로 나열되는 경우다. §1.3의 실측이 이 문제가 기존 하네스에 실재함을 보인다.

### 5.2 규정하는 크기 기준

| 대상 | 기준 |
|---|---|
| 진입 파일 | 최대 200줄, 권장 50~200 |
| 주제 문서 | 각 50~150줄 |
| 분할 신호 | 300줄 이상 |
| 진입 파일의 하드 제약 | **15개 이하** |

**기존 하네스 대비**: 진입 체인 1,044줄은 상한의 5배, `harness-guide.md` 단독 377줄은 분할 신호(300줄)를 넘는다.

> 인용된 개선 수치 — AGENTS.md 600줄 → 80줄, 성공률 45% → 72%, 보안 제약 준수율 60% → 95%. **전부 단일 미검증 출처다.**

### 5.3 세션 연속성 (강의 5)

출처가 제시하는 정보 손실 계층 — 최종 산출물(코드)은 남고 **의사결정 근거("왜 옵션 B인가")가 소실된다.** 그리고 두 가지 파생 현상을 명명한다: 컨텍스트 부족 시 검증을 생략하고 급히 완료하는 **컨텍스트 불안감**, 세션마다 누적되는 **드리프트**.

권고 도구 넷: `PROGRESS.md`, `DECISIONS.md`, git 커밋 체크포인트, 초기화 흐름 표준화. 그리고 **컨텍스트 60% 이상 사용이 예상되면 핸드오프를 준비**하라는 기준.

**기존 하네스와의 관계**: `dev-context.json`이 `PROGRESS.md` 역할을, spec의 `## 4. 의사결정` 섹션이 `DECISIONS.md` 역할을 부분적으로 한다. 다만 의사결정은 **토픽 단위 문서 안에** 있어 토픽 종료 시 아카이브된다 — [워크플로우 조사 §3.2](workflow-and-feature-list.md)가 지적한 것과 같은 구조다.

> 인용 수치 — 상태 파일 없음: 재구축 15분·완성도 58%·숨은 결함 43% / 있음: 3분·100%·8%. **미검증.**

## 6. 세 자료가 같은 방향을 가리키는 지점

서로 다른 근거 등급의 자료가 일치하는 항목만 모았다. 일치가 진리를 보장하지는 않지만, 단일 출처 의존을 줄인다.

| 주장 | 1차(도구) | 피어리뷰/측정 | 자가출판 | 배포 조사 §6.3 |
|---|---|---|---|---|
| 상시 파일은 작아야 한다 | ✅ `/doctor` | ✅ §3.2 절벽 | ✅ 50~200줄 | ✅ 200줄 인용 |
| **코드에서 유도 가능한 것은 빼라** | ✅ `/doctor` 기준 | **✅ ETH — §6.1** | ✅ | ✅ |
| 라우팅 표면에 예산이 필요하다 | ✅ 1,536자 상한 | — | — | — |
| 위치가 중요하다 | — | ✅ Liu et al. | ✅ | — |
| 압축이 규칙을 지운다 | ✅ PreCompact 차단 지점 | ✅ Governance Decay | — | — |
| 예산은 측정으로 정한다 | ✅ `/context all` | ✅ 20% 여유 권고 | ❌ 상수 제시 | — |

**마지막 행이 갈린다.** 자가출판 출처는 50~200줄이라는 상수를 제시하는데, 측정 근거 쪽은 절벽 위치가 모델마다 달라 상수가 성립하지 않는다고 본다.

### 6.1 2행의 빈 칸이 채워졌다 — 그리고 1행을 흔든다

> **2026-08-02 출처 감사 보강.** 최초 작성 시 "코드에서 유도 가능한 것은 빼라"는 도구 근거(`/doctor`)와 자가출판만 있고 측정 근거가 없었다. 그 부분에 들어가는 자료를 확인했다.

[Gloaguen et al., *Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?* (arXiv 2602.11988, ETH Zurich + LogicStar.ai)](https://arxiv.org/abs/2602.11988)는 AGENTbench로 컨텍스트 파일 유무를 대조했고 결론이 이렇다.

> *"providing context files does not generally improve task success rates, while increasing inference cost by over 20% on average"*
> *"instructions in the context files are well followed by coding agents, repository overviews, although popular and recommended by model providers, are not helpful"*
> *"context files are useful for specifying non-standard coding practices"*

**2행에 대해서는 강한 지지다.** 무용하다고 지목된 "저장소 개요"가 정확히 *코드를 읽으면 알 수 있는 것*이고, 유용하다고 지목된 "비표준 코딩 관행"이 정확히 *코드를 읽어도 알 수 없는 것*이다. 도구(`/doctor`)의 판단 기준과 독립적으로 같은 경계를 그린다.

**그런데 1행에는 불리하다.** 이 문서의 1행은 "상시 파일은 작아야 한다"인데, 원문의 주장은 **길이가 아니라 종류**다. 그리고 "개발자가 작성한 파일도 마찬가지"라는 부분이 자가출판 출처의 처방("사람이 다듬은 간결한 파일로 200줄 안쪽")을 직접 반박한다 — 사람이 썼다는 것 자체는 도움이 되지 않았다.

| | 이 문서 1행의 전제 | ETH 원문 |
|---|---|---|
| 조절 변수 | **길이** | **내용 종류** |
| 사람 작성의 효과 | 암묵적으로 긍정 | *"both LLM-generated and developer-committed"* 모두 개선 없음 |
| 처방 | 200줄 이하로 줄여라 | 저장소 개요를 빼고 비표준 관행만 남겨라 |

### 8.2 B1 — `@import` 규칙의 압축 생존

**이 조사에서 가장 날카로운 질문(§7-1)이다.** §4.1이 *생존하면 위반율 0%, 제거되면 38%* 라는 분해를 보였고 §4.2가 `PreCompact` 차단 지점을 보였는데, 둘을 연결한 자료가 없다.

#### 8.2.1 무엇을 재는가 — 텍스트 잔존이 아니라 행동 제약

**"압축 후 규칙 문장이 컨텍스트에 남아 있는가"를 재면 안 된다.** §4.1이 잰 것은 **위반율**이다. 텍스트가 남아도 안 지켜지면 의미가 없고, 요약본에 녹아들어도 지켜지면 생존한 것이다.

**따라서 판정은 행동으로 한다.** 회상(recall)은 보조 지표로만 쓴다.

#### 8.2.2 준비 — 격리 프로젝트

**하네스·grid fin·cygnus 저장소에서 하지 말 것.** 임시 디렉터리에 새 프로젝트를 만든다.

`CLAUDE.md`:
```markdown
# 프로브 프로젝트

@.probe/rules.md
```

`.probe/rules.md` — **규칙 3개.** 하나면 표본이 1이라 판정이 불가능하다.

```markdown
# 프로젝트 규칙 (반드시 준수)

- **R1**: 파일을 새로 만들 때 첫 줄에 `<!-- R1 -->` 주석을 넣는다.
- **R2**: Bash 명령을 실행할 때는 항상 `--` 를 명령 끝에 붙이지 않는다. 대신 실행 직전에 그 명령의 목적을 한 문장으로 먼저 말한다.
- **R3**: 응답을 마칠 때 마지막 줄에 `[R3]` 을 붙인다.
```

**규칙 선정 기준 넷.**

| 기준 | 이유 |
|---|---|
| 기계로 판정 가능 | 사람 판단이 들어가면 관측자 편향이 생긴다 |
| 모델의 기본 행동과 겹치지 않음 | 겹치면 규칙 없이도 지켜져 구분이 안 된다 |
| 무해함 | 위반해도 손해가 없어야 여러 번 돌릴 수 있다 |
| 서로 다른 종류 | R1은 파일 산출, R2는 발화 순서, R3은 응답 형식 — **한 종류만 쓰면 그 종류의 특성을 압축 효과로 오인한다** |

#### 8.2.3 3단계 측정

| 단계 | 조건 | 목적 |
|---|---|---|
| **A. 기준선** | 압축 전 | 규칙이 애초에 지켜지는지 |
| **B. 압축 후** | `/compact` 직후 | §7-1의 본 질문 |
| **C. 훅 개입 후** | `PreCompact` 훅으로 규칙 재주입 + 압축 | §4.2의 차단 지점이 실제로 듣는지 |

**각 단계에서 같은 과제 세트를 돌린다.** 규칙 3개를 모두 발동시키는 작업 **10회**를 준비해 순서를 고정한다. 예: *"`notes/<n>.md` 파일을 만들고 한 줄 적어라"* (R1·R3 발동, 파일 생성이므로 R2도 자주 발동).

**판정**: 각 단계의 **규칙별 준수 횟수 / 10**.

> **왜 10회인가.** [평가 §6.4.1](evaluation.md)의 `n ∝ 1/δ²`을 적용한다. §4.1이 보고한 효과는 **0% → 38%** 로 `δ ≈ 0.38`이며, 그 크기라면 필요 표본이 10 아래로 내려간다. **10회는 "규칙이 통째로 사라지는" 큰 효과를 잡기에 충분하고, 부분적 열화를 잡기에는 부족하다.** 결과가 애매하면(예: 10→7) 표본을 늘려야 하며, 그때는 §6.4.1의 표를 다시 보고 필요 수를 계산할 것.

#### 8.2.4 단계 B의 절차

1. A 완료 후 `/compact` 실행
2. **압축 직후 아무 작업 전에** 회상 지표를 먼저 잰다 — *"이 프로젝트의 규칙 세 개를 그대로 인용해라"*
   - **회상 성공 ≠ 생존이다.** 물어보는 행위 자체가 규칙을 컨텍스트로 되불러올 수 있으므로 **이 질문은 B 과제 10회보다 먼저, 단 한 번만** 한다
3. 과제 10회 실행, 규칙별 준수 횟수 기록
4. `/context all`을 한 번 더 찍어 **CLAUDE.md 체인이 압축 후에도 컨텍스트에 있는지** 확인

**4번이 교란 통제의 핵심이다.** Claude Code가 매 턴 CLAUDE.md를 재주입한다면 압축은 애초에 규칙을 지울 수 없고, **이 실험 전체가 무의미해진다.** §7-2가 *"생존 여부를 관측할 수 있는가"* 를 따로 물은 이유가 이것이다. **B를 돌리기 전에 4번을 먼저 확인하는 편이 낫다.**

#### 8.2.5 단계 C의 절차

`.claude/settings.json`에 `PreCompact` 훅을 건다. **[실험 B6](enforcement-mechanisms.md)이 확인한 대로 `settings.json`에 넣어야 한다 — `.claude/hooks/hooks.json`은 읽히지 않는다.**

```json
{ "hooks": { "PreCompact": [ { "hooks": [ { "type": "command",
  "command": "cat .probe/rules.md" } ] } ] } }
```

훅 stdout이 압축 결과에 주입되는지가 미확인이므로, **차단(`exit 2`) 방식과 주입 방식 둘 다 시험할 가치가 있다.** §4.2의 changelog는 *차단*만 명시한다.

그 뒤 A와 같은 과제 10회.

#### 8.2.6 판정 기준

| 관측 | 해석 |
|---|---|
| A ≈ B (둘 다 높음) | **규칙이 압축에서 생존한다.** §7-1이 닫히고 `PreCompact` 개입이 불필요 |
| A 높음, B 낮음 | **§4.1의 Governance Decay가 이 도구에서 재현된다.** C가 회복시키는지가 다음 질문 |

| B 낮고 C 높음 | **`PreCompact`가 완화책으로 동작한다.** §4.1의 Constraint Pinning에 대응하는 실무 형태를 얻은 것 |

### 10.4 답과 그 이유

**§7-1이 닫힌다 — `@import`된 규칙은 압축에서 살아남는다.** 그리고 **왜 그런지가 구조적으로 설명된다.**

**`CLAUDE.md`와 `@import` 대상은 대화 히스토리가 아니라 별도의 memory 채널로 주입된다.** `/context all`이 `Memory files`와 `Messages`를 다른 범주로 세는 것이 그 증거다. **압축은 `Messages`를 요약해 대체하는 동작이므로 memory 채널을 건드리지 않는다.**

**[§4.1의 Governance Decay가 이 경로에는 해당하지 않는다.](#41-governance-decay)** 그 실험(ConstraintRot, 7개 계열 1,323 에피소드)은 **제약이 대화 컨텍스트 안에 있는** 설정을 가정한다. Claude Code의 `@import`는 그 설정이 아니다.

**§7-2(생존 여부를 관측할 수 있는가)도 닫힌다** — `/context all`의 Memory Files 절이 관측 경로다.

**§4.2의 `PreCompact` 훅은 이 목적으로는 불필요하다.** 압축이 규칙을 지우지 않으므로 막을 이유가 없다. **프로토콜의 C단계(훅 개입)는 실행하지 않았고, 실행할 근거가 사라졌다.**

### 10.5 방법론 기록 — 거짓 발견을 한 번 잡았다

**압축 후 `/context all` 출력을 처음에 30줄까지만 읽었다.** Memory Files 표가 그 경계에서 잘려 `.probe/rules.md` 행이 보이지 않았고, **"압축이 import를 지웠다"는 정반대 결론에 도달할 뻔했다.**

**총 토큰이 압축 전후로 242로 동일하다는 점이 어긋났고, 그것을 단서로 전문을 다시 읽어 잡았다.**

**이 시리즈가 반복해서 겪은 것과 같은 형태다** — [평가 §1.6.3.1](evaluation.md)의 `pass^k` 오귀속은 다섯 번째 폴백에서, 이것은 산술 불일치에서 잡혔다. **출력을 잘라 읽는 것이 2차 인용과 같은 등급의 위험이다.**

### 10.6 이 실험이 답하지 않은 것 — 한계가 크다

1. **압축이 사소했다.** 컨텍스트가 1턴이었고 `Messages`가 4.1k였다. **긴 세션의 손실성 압축에서도 같은지 확인하지 않았다.** 다만 §10.4의 기제(별도 채널)가 맞다면 길이와 무관해야 한다 — **그 추론을 검증하지 않았다.**
2. **자동 압축(auto-compact)을 시험하지 않았다.** `/compact` 수동 경로만 확인했고, 둘이 같은 코드 경로인지 모른다.
3. **규칙이 둘뿐이고 무해한 형식 규칙이다.** §8.2.8이 미리 적은 대로 §4.1의 "거버넌스 제약"과 종류가 다르다.
4. **과제 3회는 §8.2.3이 정한 10회에 못 미친다.** 위반이 0건이라 조기 종료했으나, **부분적 열화를 잡기에는 부족하다.** [평가 §6.4.1](evaluation.md) 기준으로 3회는 큰 효과만 본다.
5. **규칙 준수가 압축과 무관하게 성립했을 가능성** — 기준선(압축 전) 표본이 2회뿐이다. A와 B 모두 100%라 **차이를 잴 수 없다.** "떨어지지 않았다"까지가 이 실험의 결론이고 "떨어질 수 없다"가 아니다.
