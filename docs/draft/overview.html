1. 무엇을 고치는가

이 설계는 워크플로우를 발명하지 않는다. 참고 하네스의 계층과 상태 기계는 여러 프로젝트를 완주했고(원장 H1), 바꾸는 것은 그 아래 인프라다. 단계는 거의 그대로이고, 각 단계가 무엇을 읽고 쓰는지가 달라진다.

1-1. 실측된 결손 7개 — 전부 조용히 실패했다

결손무엇이 일어났나어디서 고치나
핀이 gitignore 안에 있었다 deploy-harness.sh가 심는 ignore 블록이 매니페스트 자신을 포함했다. 추적되지 않는 핀은 핀이 아니다 — 어느 버전을 쓰는지 알 방법이 없다 §6-1 ⓪의 ★ 훅 등록 확인이 매니페스트도 본다 · 워크트리 쪽은 ③의 ★ 배포물 확인(원장 S26)
훅 등록이 조용히 통과했다 세션 시작 가능 디렉터리마다 설정 + 스크립트가 필요한데 없으면 검사가 실패하는 게 아니라 사라진다. 계산적 게이트 전부가 그 위에 선다
이 설계에서 그 디렉터리는 하나다 — 루트에서만 시작하고 워크트리는 커밋이 덮는다(§6-1 · 원장 S10)		 §6-1 ⓪의 ★ 훅 등록 확인 · 원장 S10
스펙·계획이 git 밖에 있었다 머신 경계를 넘지 못했다 — 스펙을 작성한 머신이 아니면 그 작업의 존재를 알 수 없다 §7-2 — 이슈 본문 · 작업 브랜치 · 정본 문서 3개로 가른다
하네스 레벨 학습의 44%가 유실됐다 진행 중인 프로젝트에서 고친 것이 원본에 전파되지 않았다. 배포는 있고 원본 반영이 없었다 §4-9 — 지적의 귀속을 관측으로 가른다
완료된 기능의 상태를 답할 것이 없었다 토픽이 끝나면 산출물은 아카이브가 되고, 상태 파일은 진행 중인 것만 담았다 §4-1 — L0를 세운다. 다만 구조 파일은 두지 않는다
타입 검사가 실행되고도 신호를 버렸다 type-check.js가 .ts 편집마다 프로젝트 전체 tsc --noEmit(30초 상한)을 돌리고 결과를 console.warn + exit 0으로 흘렸다. 종료 코드 0의 출력은 모델에게 도달하지 않는다(1차 실측, §5-2 실측 4). 등록은 있는데 신호가 없다 §5-2 — 쓰기 후 상태가 필요한 검사는 커밋 경계로
상태와 설정이 한 파일에 섞여 있었다 config.* 18키가 공유 축이 다른 5개 부류인데 한 파일이라, git에 넣으면 머신별 값이 충돌하고 원격에 올리면 공유하면 안 되는 값이 오염된다 §7-3 — 층 5개 + 층 밖 2개
일곱의 공통 성질이 이 설계의 방향을 정한다 — 전부 「실패」가 아니라 「부재」로 나타났다. 검사가 빨간불을 켠 것이 아니라 검사가 없었던 것처럼 지나갔다. 그래서 이 설계의 강제 지점은 전부 결정적 조건이다 — 등록이 있나 · 배포물이 추적되나 · 도구가 있나 · 번호가 있나 · 쓸 수 있는 경로인가 · 게이트를 통과했나 · 판정 기록이 있나. 판단이 필요한 것은 차단하지 않는다(§5-2).

일곱째는 앞의 6개와 형태가 다르고, 그래서 따로 세었다. 앞의 6개는 있어야 할 것이 없어서 검사가 사라졌다. 일곱째는 등록이 있고 스크립트가 실행됐는데 결과를 버렸다. ⓪의 ★ 훅 등록 확인은 이것을 잡지 못한다 — 선언과 파일은 짝이 맞기 때문이다. 그래서 고치는 곳이 설치 시점이 아니라 배치다(§5-2).

1-2. 참고 하네스가 어디까지 왔나

아래 세 계층은 이름만 바뀌었고, 실제로 바뀌는 것은 계층이 아니다. 종착만 한 칸 더 간다 — 참고 하네스의 토픽은 PR 생성에서 끝났고 이 설계는 머지까지 간다.

참고 하네스이 설계실체
topic (종료 = pr:created)story이미 여러 프로젝트를 돌아본 구조
story (Commit: 1개)task이미 돌아본 구조
task (- [ ] T1.1)sub task이미 돌아본 구조
—epic · area새것 (§4-4)
상태 기계 자체는 이름이 겹치지 않는다 — 참고 하네스의 전이표를 직접 읽으면 이렇다. 
spec:drafting → spec:reviewing → spec:confirmed → plan:ready → plan:reviewing
 → plan:confirmed → impl:in-progress → review:in-progress → docs:generated → pr:created

되돌림 spec:reviewing → spec:drafting plan:reviewing → plan:ready
 review:in-progress → impl:in-progress // 주석: 리뷰 실패 → 재구현
 docs:generated → review:in-progress pr:created → docs:generated
여기서 확인되는 것 4개.

㉠ 종착이 pr:created이지 머지가 아니다. 참고 하네스의 토픽 상태 기계는 PR 생성에서 끝나고 머지는 상태 밖이었다. 이 설계는 integrated(머지)를 종착으로 둔다 — 한 칸 더 간다. 그래야 Closes #N이 이슈를 닫는 사건과 종착이 일치한다.

㉡ review:in-progress → impl:in-progress가 실재했고 주석이 “리뷰 실패 → 재구현”이다. 이 설계의 ⓐ 수정해서 진행이 그 간선이다 — 새로 만든 것이 아니다.

㉢ 스펙·계획 리뷰가 각각 되돌림 간선을 갖고 있었다(spec:reviewing → spec:drafting, plan:reviewing → plan:ready). §5-2의 검토 1·2번과 라운드 상한이 여기 실물로 있었다 — 그래서 2개 다 두기로 했다(원장 S13 · 상한 3회는 S14).

㉣ verify에는 상태가 없었다. review:in-progress → docs:generated 사이에서 실행되지만 전이표에 이름이 없다 — 게이트이지 상태가 아니었다. 이 설계가 그것을 reviewed → integrated의 HEAD 일치 가드로 둔 것이 같은 성질이다(원장 S5).

그리고 없던 것 하나 — review에서 spec으로 돌아가는 간선은 참고 하네스에 없다. review:in-progress에서 갈 수 있는 곳은 impl과 docs뿐이었다. 이 설계의 ⓑ 「스펙부터 다시」는 새것이다 — 물려받은 것이 아니라 추가한 것이므로 그렇게 읽어야 한다.
상태 어휘는 참고 하네스와 이름이 겹치는데, 하나만 같은 것이다.

reviewed = /flow-review — “Perform a final full code review. Runs code-reviewer and security-reviewer in parallel, then adversarial-review sequentially (opt-in)”. 추론적 리뷰이고 통합 전이며 PR의 전제다. 같다.

verified ≠ /flow-verify — 참고 하네스의 verify는 “Run the full verification gate before generating the reference document. Checks build, type-check, lint, test, and security in order”로 리뷰가 끝난 뒤 전체를 다시 검증하는 것이었다. 이 설계의 verified는 task 커밋 경계 게이트의 집계다 — 대상이 다르고(전체 ⇄ 개별 커밋) 시점이 다르다(리뷰 후 ⇄ 리뷰 전).

이름이 같아서 대응하는 것처럼 보이므로 적어 둔다. 참고 하네스의 verify에 해당하는 것은 이 설계에서 단계가 아니라 reviewed → integrated의 HEAD 일치 가드다(§6-3 도해).
「Feature」도 이름이 겹치는데 뜻이 다르다 — 한 칸 밀려 있다.

Azure DevOps의 계층은 “Epics group Features, Features group Requirements (User Stories …), and Requirements group Tasks”이고, 거기서 Feature는 크기 계층이자 작업 항목이며 완료된다.

산업의 Feature에 대응하는 것은 이 설계의 epic이다 — 유한하고 story를 묶는다. 그리고 이 설계가 「피쳐 목록」이라 부르는 것(L0)은 작업 항목이 아니고 완료되지도 않으므로 산업에 대응하는 작업 항목이 없다.

이름을 바꾸지 않는 이유 — 조사 문서가 “피쳐 목록 부재”를 이 설계 전체의 상위 항목으로 못박았고, 어휘를 바꾸면 근거 문서와 설계 문서의 용어가 갈린다. 대신 여기 적어 둔다 — verified ≠ /flow-verify(§1-2)와 같은 부류의 함정이다.

계층에 관한 위험은 낮다. 실제로 바뀌는 것은 계층이 아니라 원장의 관찰 항목 4개이다 — 전이 권한(체크박스 편집 → 산출물, Q1) · 판정 방식(종료 코드 → 결과 객체, Q2) · 리뷰 위치(전부 PR 이전 → 계산적 검사는 통합 전, 추론적 검토는 5개 단계에 나눠 — Q3) · 빌드 깨짐 허용(예외 경로 신설, Q4).

2. 설계 원칙

여덟 원칙이 이후의 모든 결정을 판정한다. 이 문서에서 “왜 그렇게 정했나”가 나오면 대개 이 표의 한 줄로 돌아온다.

#원칙어느 계층근거등급
P1story는 단위 테스트가 가능한 PR 최소 단위다. 목표 수십 줄 · 1~5파일L1 실증된 리뷰 단위 중앙값 24~44줄 / 1~5파일, 리뷰어 1~2명에서 수확 체감. story=PR로 두면 그 수치가 원문이 실제로 잰 대상에 걸린다. 남는 한정어 하나 — 두 문헌 모두 사람 리뷰어 대상이고 에이전트 전이는 미검증 피어리뷰
P2상태는 실행된 산출물이 뒷받침할 때만 존재한다. 승인·체크박스는 상태가 아니다L1·L2·L3 판정자와 기록자가 같으면 상태가 의미를 잃는다(실측). “검증 명령만이 전이를 허용한다”는 형식 규정 자체는 채택하지 않았다 — 단일 자가출판이고 보류 분류다 구조적 논증 + 1차 실측
P3판정은 종료 코드가 아니라 결과 객체 + 기대값 대조다L2 종료 코드는 런타임 간 정규화되지 않는다(vitest 1 / nextest 100). JUnit XML은 정규화된다. fail-open이 계층을 바꿔가며 6개 번 재현됐다 1차 실측
P4게이트는 판정 방식과 되돌림 비용이 함께 정한다. 계산적 = 통합 전·차단, 추론적 = 되돌리기 싸면 — 지적을 리뷰어가 고칠 수 있으면 고치고 못 고치면 정지, 아니면 라운드 상한 · 되돌릴 수 없으면 비차단(§5-2)L2↔L3 차단은 effective false positive 0%일 때만, 비차단 계층은 10%까지 허용하고 초과하면 끈다(Google CACM 2018). 계산적은 통합 전 / 추론적은 통합 후(Fowler) 피어리뷰 + 1차
P5강제하는 것은 순서가 아니라 사이클의 크기와 일정함이다L2 “Sequencing, the order in which test and production code are written, had no important influence” — 효과는 granularity와 uniformity가 냈다 (Fucci et al., IEEE TSE 2017) 피어리뷰
P6첫 story는 Walking Skeleton이고 스텁을 쓰지 않는다. 픽스처는 허용L1 정의가 “a real end-to-end test with no stubs”. 판별선은 반환값이 계산된 것인가 박힌 것인가 1차(정의)
P7규칙은 모델 지시가 아니라 훅·설정·권한으로 표현한다전 계층 지시 500개에서 최고 모델도 68%로 급락(IFScale). 경계 3분류(항상/확인/금지)가 allow/ask/deny에 대응한다 프리프린트 + 1차
P8병렬은 사람이 미리 가른 독립 구간에만, 워크트리 격리로. 에이전트가 에이전트에게 실시간 위임하지 않는다L1 부적합 조건은 실시간 위임 / 컨텍스트 공유 / 의존성 많음 3개고 워크트리 병렬은 그 반대편이다. 하네스 12종이 전부 워크트리 병렬을 전제로 만들어졌다 피어리뷰(NeurIPS 2025 D&B) + 1차

3. 전체 그림 — 상태 축 4계층 × 상태를 갖지 않는 두 축

계층을 가르는 기준은 원자 단위와 종료 조건이다. 둘이 달라지면 다른 계층이다. 그리고 계층마다 게이트의 성격이 다르다 — 아래로 갈수록 결정적이고, 위로 갈수록 추론적이다.

여기에 직교하는 축이 하나 더 있다. area와 epic은 계층이 아니라 그룹핑 필드다 — 자체 상태 기계를 갖지 않고 작업 항목에 붙는다.

3-1. 축이 4개다 — 이 문서를 읽는 지도

아래 네 축은 같은 설계를 다른 각도에서 자른 것이다. 한 축만 읽어도 말이 되지만, 모순은 축을 겹칠 때만 보인다 — 실제로 이 문서의 오류 둘이 그렇게 발견됐다(원장 S3·S4).

계층무엇이 있는가 — 원자 단위와 종료 조건으로 가른다§4
판정무엇이 통과를 정하는가 — 형태 · 어댑터 · 게이트 · 리뷰§5
흐름언제 무엇이 일어나는가 — 설치부터 정리까지, 그리고 상태 기계§6
저장무엇이 어디 사는가 — 정본 · 작업 문서 · 설정§7

추상에서 구체로 간다 — 계층이 가장 추상적이고 저장이 가장 구현에 가깝다. 급하면 §4와 §6만 읽어도 전체가 선다.

8. 대조 — 산업 표준

단일 규범이 없다 — 그래서 이 설계는 어느 표준을 어긴 것이 아니다. 형태는 Azure DevOps에 가깝고, 가장 큰 차이는 계층 수가 아니라 크기를 무엇으로 정의하느냐다.

형태는 Azure DevOps에 가깝고, Jira 기본 계층으로는 표현되지 않는다(task를 story 아래 2개 수 없다). 가장 큰 차이는 계층 수가 아니라 크기를 무엇으로 정의하느냐다 — 표준은 시간·노력, 이 설계는 산출물이다. 추정은 사후 검증할 수 없지만 커밋은 존재하거나 존재하지 않는다(P2).

그리고 XP의 두 기준이 이미 맞물린다 — story의 Testable(INVEST)과 task의 Measurable(SMART, 정의에 “tests are included”가 들어 있다). 근거: epic·story·task 조사.

한 가지 긴장 — INVEST의 Independent는 “어떤 순서로도 구현할 수 있어야 한다”인데, 대규모 마이그레이션을 story 여러 개로 쪼개면 순서 의존이 생긴다. XP 원저자도 “We can't always achieve this”로 단서를 단다. Strangler Fig가 실무적 답이다 — 슬라이스마다 독립 배포·롤백이 되게 자르면 Independent가 회복된다. story 분할 기준으로 쓸 만하다.

9. 다음 — 가장 작은 규모로 한 번 실행

미결은 이 문서가 관리하지 않는다 — 미결 사항 원장이 원본이고, 이 문서는 필요한 곳에서 ID를 인용하되 내용을 한 줄 붙인다 — ID만 적으면 읽는 사람이 원장을 열어야 하고, 목록을 복제하면 한정어가 빠진다. 그 사이가 한 줄이다. 목록도 건수도 여기에 적지 않는다 — 복제하면 요약 층에서 한정어가 빠지고, 이 저장소가 그 이유로 두 번 감사했다.

어떻게 진행하는가 — 하나만. 스펙을 더 쓰지 말고 가장 작은 규모로 한 번 실행 돌린다. epic 1개 → story 1개 → task 2~3개.

근거 2개 — ① 개인 규모에서 이 설계를 검증할 통계적 수단이 없다(δ≈0.02 → 문항 약 2,180개). 남는 검증은 실제로 아파 보는 것뿐이다. ② 그게 P6(Walking Skeleton)이고, 하네스 자신에게 먼저 적용하지 않을 이유가 없다.
