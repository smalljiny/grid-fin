6. 흐름 — 언제 무엇이 일어나는가

§4가 무엇이 있는가를 계층으로 잘랐다면, 이 축은 시간으로 자른다. 계층을 다 읽은 뒤라야 각 단계가 어디에 앉는지 보인다.

6-1. 단계 열넷 — 설치부터 정리까지

설치에서 정리까지 열네 단계다. 그중 하드 차단은 일곱이고 둘씩 설치와 구현에 몰려 있으며, 외부 원장을 요구하는 단계는 셋뿐이다.

⓪설치대상 프로젝트에 하네스를 넣는다 ★ 훅 배선 검증 · ★ 배포물 추적 확인갱신은 3-way merge. 검사는 update 앞에

+ 코드 검토 — 고치고, 못 고치는 것만 정지(★가 아니다. 심각도 판정은 추론이라 오탐이 있다)		 외부 원장 없이 돈다 — git과 로컬 파일만
⑤′story 리뷰 브랜치 전체 — PR로 갈 것인가. 사람이 셋 중 고른다: 통과 →reviewed / ⓐ 수정해서 진행(→baseline) / ⓑ 스펙부터 다시(→proposed) 라운드 상한 · 자동으로 되돌리지 않는다 로컬. 진짜 취소가 가능한 마지막 단계이고 ⑦의 전제조건이다 — 리뷰가 안 돌면 reviewed에 못 가고 머지도 못 한다. ⑦의 PR 리뷰와 합치지 않는다(원장 S15)
⑥상태 확인산출물을 조회해 현재 상태를 계산한다 — 옮기지 않는다(원장 S12) — 강제가 구조에 흡수됐다외부 원장 없이 — 계산 재료가 전부 작업 브랜치의 git이다
⑥′정본 반영 L1 → L0 승격 — product.md와 구현의 정합성 대조. 바뀔 것이 있으면 갱신하고 단일 커밋, 없으면 「L0 반영: 없음(이유)」(§4-2) ★ 정합성 판정 기록이 있어야 머지로 간다 — 커밋 또는 「없음(이유)」 코멘트 로컬. PR이 이 문서를 참조한다. ⑤′ 리뷰를 다시 받지 않는다 — 아래 참조
⑦통합PR 리뷰 — 통합해도 되나 → push · PR · 머지라운드 상한마지막 되돌림 지점
⑧리뷰 추론적 게이트 → 별도 이슈 + L3 계수기(§4-9) —비차단 — 진행을 판정하지 않는다(§5-2)
⑨정리워크트리 · 계획 문서 소멸 마지막이면 .worktrees 부모도 제거세션 레코드는 TTL로 만료 — 종료 훅에 의존하지 않는다
검토와 구현을 실제로 실행하는 것은 서브에이전트 넷이다(원장 S20) — 어느 단계에서 무엇을 부르는지가 여기서 정해진다.
무엇어느 단계에서권한이 다르다
코드 검토자⑤ 커밋 경계 · ⑤′ 브랜치 전체 · ⑦ PR · ⑧ 통합 후 ⑤는 고친다(못 고치면 정지) · ⑧은 의견만 — 되돌릴 수 없기 때문이다
보안 검토자⑤′에서 코드 검토자와 병렬—
문서 검토자③′ 스펙 · ④′ 계획 고치지 않는다 — 다시 작성해야 하는 종류다(§5-2)
구현자⑤작업 종류별로 갈린다. 어댑터가 검증을 맡고 이쪽은 작성

하나가 넷이 아니라 「대상과 권한이 다른 호출」이다 — 참고 하네스도 코드 검토자 하나를 구현 단계에서는 자동 수정으로, 브랜치 검토에서는 전체 검토로 불렀다(1차, 직접 확인).

심각도 기준과 모델은 각 서브에이전트 파일 안에 있다 — 기준·모델·검토자가 함께 배포되고 함께 핀이 박힌다(§7-4).

이것이 배선과 다른 층이라는 점이 중요하다. 배선은 언제 자동으로 도는가이고, 서브에이전트는 무엇이 실행하는가다. 검토는 명령이 부르므로 배선이 늘지 않는다.
「배선」이란 — 검사가 언제 불려 나가는지를 정하는 연결이다. 게이트가 검사 자체라면, 배선은 그것을 사건에 붙이는 두 조각이다.

① 선언   설정 파일 — 어느 사건에 무엇을 부를지
     SessionStart → 도구 설치 검사
     PreToolUse   → 쓰기 직전 차단 (§5-2의 첫 경계)
     PreToolUse   → 커밋 직전 차단 (둘째 경계) + 코드 검토
     PostToolUse  → 포맷 교정 (차단하지 않는다)
② 스크립트  실제로 도는 것
둘이 다 있어야 검사가 돈다 — 선언만 있고 스크립트가 없으면 안 돌고, 반대도 마찬가지다. 참고 하네스가 이렇게 하고 있었다 — 설정 파일이 네 사건에 훅 항목 아홉을 걸고 있었다(고유 스크립트는 여덟. 1차, 직접 확인).

「디렉터리마다」인 이유 — 설정 파일이 상속되지 않는다. 세션이 시작될 수 있는 디렉터리마다 그 파일이 따로 있어야 한다 — 그런데 그 디렉터리가 몇인지는 아래에서 하나로 줄어든다.

⚠ 2026-08-09 정정 — 워크트리는 그 목록에서 빠진다. 이 대목은 원래 “메인 하나, 워크트리마다 하나씩 … 그 수가 진행 중인 작업 수에 비례해 늘어난다. ③ 착수가 배선을 함께 심지 않으면 그 워크트리에는 게이트가 없다”고 적었다. 실측으로 틀렸다(원장 S10 정정). git worktree add는 추적 파일을 체크아웃하므로 설정도 스크립트도 실행 비트까지 그대로 따라온다. 워크트리에서 세션을 열자 훅이 발화했고 CLAUDE_PROJECT_DIR이 워크트리 루트를 가리켰다. ③ 착수는 아무것도 심지 않는다.

정확히 말하면 — 파일 수는 루트 수만큼이지만 심는 동작은 한 번이다(커밋). 그래서 배선이 추적되는 것이 우연이 아니라 요건이다 — .claude/settings.json과 훅 스크립트가 .gitignore에 걸리면 워크트리 전부가 게이트를 잃는다. §1-1의 첫째 결손이 정확히 같은 문제였다(핀이 gitignore 안에 있었다).
그래서 ⓪의 ★ 하나가 넓어진다 — 「핀 추적 확인」이 「배포물 추적 확인」이 된다. 매니페스트만이 아니라 .claude/settings.json과 훅 스크립트까지 git ls-files로 대조한다. ★를 늘리지 않는 이유는 검사가 같기 때문이다 — 배포된 것이 추적되는가. §1-1의 첫째 결손과 이것이 같은 문제라 한 ★가 둘 다 본다.

그리고 ⓪의 ★ 배선 검증이 간단해진다 — 커밋된 트리 하나를 보면 현재와 미래의 워크트리 전부가 덮인다. 살아 있는 워크트리를 열거하지 않아도 된다.
그래서 배선이 놓이는 곳은 하나다 — N = 1. 저장소 루트의 .claude/settings.json과 .claude/scripts/, 전부 추적된다. ⓪ 설치가 한 번 심고 커밋하면 끝이고, ③ 착수는 워크트리를 만들 뿐 배선을 심지 않는다.

settings.local.json은 배선에 쓰지 않는다 — 근거 셋. ① 이 머신에서는 추적되지 않는다(전역 gitignore의 한 줄). 그 줄이 없는 머신에서는 추적된다 — ①은 근거가 아니라 결함 그 자체다: 추적 여부가 머신마다 갈린다. ② 핀이 붙지 않는다(3-way merge가 덮어쓰기로 퇴화). ③ 위치 독립성이 실측으로 없다 — 아래. ②·③만으로 기각이 성립한다.
공식 문서가 settings.local.json에 대해 적은 것이 이 판에서 성립하지 않는다. 문서는 “Claude Code reads and writes this file at the root of the git repository, resolved through worktrees to the main checkout, so one file covers sessions started in any subdirectory or worktree of the repository”라고 적는다. 세 곳에서 재니 루트에서만 발화했다 — 하위 디렉터리 ✗(2회 재현) · 워크트리 ✗ (1차 실측, 2026-08-09 · Claude Code 2.1.226).

직접 둔 파일에 대해서는 저장소 루트 해석이 읽기 쪽에 아예 없다. 하위에 그 파일을 직접 두자 발화했고 CLAUDE_PROJECT_DIR이 저장소 루트가 아니라 그 하위 디렉터리를 가리켰다. settings.local.json은 settings.json과 같은 규칙으로 동작한다.

그래서 CLAUDE_PROJECT_DIR은 「저장소 루트」가 아니라 「설정을 찾은 디렉터리」다. 훅 명령을 그 변수 기준으로 쓰는 것은 루트에서 시작한다는 전제 위에서만 맞는다.
그 전제는 규약이고, 규약 위반은 조용하다 — 이 설계가 안고 가는 대가다. 하위 디렉터리에서 세션을 시작하면 설정이 상속되지 않아 훅도 permissions.deny도 사라진다(1차 실측). 그런데 스킬은 상속된다 — 같은 조건에서 하네스 명령은 전부 보였다(1차 실측).

둘이 겹쳐서 최악의 조합이 된다 — 하네스가 정상 동작하는 것처럼 보이면서 강제만 빠진다. 「루트에서 시작하라」를 강제할 자연 기제가 없다 — 막을 훅이 바로 그 훅이기 때문이다.

그래도 규약으로 두는 근거 — ① 이 워크플로우에서 세션은 메인 아니면 워크트리 루트에서 시작하고 ③ 착수가 그 경로를 만들어 준다. ② 디렉터리마다 사본을 두어도 등록되지 않은 디렉터리는 여전히 조용하다 — 관리 포인트를 늘려도 구멍이 남는다. 대가를 적어 두고 안고 간다(원장 S10).
그 한 곳에 실리는 배선 항목은 넷이다 — 그리고 ★가 확인할 목록이 곧 이것이다.

무엇어디왜 자동이어야 하나
SessionStart 스크립트② 세션 시작 설정 층 해석 + 캐시(§7-3) · ★ 도구 설치 검사 · 세션 등록
PreToolUse — 파일 쓰기⑤ 쓰기 경계 §5-2의 첫 경계. 종료 코드 2로 차단(실측 1). 쓸 내용과 경로만으로 판정되는 것만 여기 있다 — 파일 경계 · 금지 패턴 · 시크릿
PreToolUse — 커밋⑤ 커밋 경계 §5-2의 둘째 경계. ★ 통합 전 차단. 목록은 §5-2 도해의 커밋 경계 — 타입과 타입 인식 린트가 여기로 내려왔다
PostToolUse — 포맷⑤ 쓰기 직후 차단하지 않는다 — 고치고, 고쳤다고 말한다. 말하는 채널은 종료 코드 0 + stdout JSON의 additionalContext(§5-2 실측 6) — stderr로 쓰면 도달하지 않는다(실측 4). 참고 하네스의 prettier-format이 이미 여기 있었다

⑥에 아무것도 없는 것이 이번 판의 변화다 — permissions.deny 규칙이 여기 있었다. 상태를 저장하지 않기로 하면서 편집할 필드가 사라졌고, 막을 것이 없어졌다(원장 S12). 강제를 뺀 것이 아니라 구조가 그것을 불가능하게 만들었다.

같은 파일에 실리지만 배선이 아닌 것 하나 — 권한 허용 목록이다(원장 S21). settings.json은 훅 선언만 담는 것이 아니라 어떤 명령을 물어보지 않고 실행할지도 담는다. 빠지면 구현 루프가 git commit마다 승인을 물어 멈춘다. 단계가 실제로 부르는 것만 넣는다 — git·gh · P1이 정한 언어 도구 둘 · 선언 설정에 적힌 검사 도구 · Skill(*). 허용 목록과 선언 설정이 연결되므로 어댑터가 쓰겠다는 도구가 허용에 없으면 ⓪에서 잡힌다.

배선이 아닌 것을 가리는 것이 이 목록을 짧게 유지한다 — 명령으로 부르는 단계(⓪·①·③·④·⑥·⑥′·⑦·⑨)와 라운드 상한이 걸린 리뷰 넷은 자동 차단이 아니므로 배선이 없다. 그리고 종료 훅을 쓰지 않는다 — 세션 레코드는 TTL이 정본이라 Stop에 의존하지 않는다(S4).

참고 하네스는 사건 넷 · 훅 항목 아홉 · 고유 스크립트 여덟이었다(1차, 직접 확인). 이 설계가 사건 셋 · 스크립트 넷으로 주는 것은 리뷰를 명령으로 두고 종료 훅을 없앤 결과다.
세면서 걸렸던 것 — 「쓰기 직전」을 무엇으로 구현하나 — 은 실측으로 닫혔다(원장 S8, 해소 2026-08-09). 쓰기 경계는 차단이 맞고(PreToolUse 종료 코드 2로 파일이 생기지 않는다), 거기 남는 것이 좁아졌을 뿐이다 — 쓸 내용과 경로로 판정되는 것만. 타입은 커밋 경계로 내려가고 포맷은 사후 교정이 된다. 실측 여섯은 §5-2에 있다.
그리고 이것이 가장 나쁜 실패 형태다 — 배선이 빠지면 검사가 「실패」하지 않고 「없었던 것처럼」 지나간다.

배선 있음 → 검사 실행 → 통과 또는 실패 — 신호가 있다
배선 없음 → 아무 일도 일어나지 않음 → 통과처럼 보인다 — 신호가 없다

둘을 바깥에서 구분할 수 없다. §1-1이 결손 일곱의 공통 성질로 뽑은 “「실패」가 아니라 「부재」로 나타났다”가 이것이고, ⓪에 ★ 배선 검증이 붙는 이유다 — 설치 시점에 「선언과 스크립트가 짝을 이루는가」를 확인하고 안 맞으면 멈춘다. 파일 존재 대조라 결정적이고 오탐이 없다.
★ 배선 검증이 사지 못하는 것을 밝혀 둔다 — 스크립트가 신호를 버리는 경우다. §1-1의 일곱째가 그 형태였다: 선언도 파일도 있고 스크립트가 돌았는데 exit 0이라 결과가 모델에게 도달하지 않았다. 파일 존재 대조로는 보이지 않는다.

설치 시점에 종료 규약을 판정하려면 스크립트를 실행해야 하므로, 여기서 약속하지 않는다. 대신 덮는 곳을 옮긴다 — 훅 스크립트는 하네스 배포 저장소에서 나오고 매니페스트로 핀이 박히므로(§7-1), 종료 규약은 하네스 자신의 코드이고 하네스 자신의 테스트가 덮는다. ★가 사는 것은 「짝이 맞는가」까지다 — 그 범위 안에서 오탐이 없다는 뜻이다.
⑥′가 리뷰를 다시 받지 않는 근거. 정본 반영은 구현이 확정된 뒤에 일어나고 선언된 문서 경로만 건드리므로 동작에 영향을 주지 않는다. 그것을 보장하는 것이 가드 ㉡이다 — 벗어나면 reviewed가 무효가 되어 리뷰를 다시 받는다.

그리고 「없음」이 만능 면제부가 되지 않게 이유를 요구한다 — verification: 없음(이유)(§5-4 나)와 같은 형태다. 선언된 부재는 결손이 아니지만, 선언되지 않은 부재는 결손이다.

6-2. 이 배치에서만 보이는 것

이 배치가 둘을 눈으로 확인시킨다 — 강제가 어디에 몇 개 붙는가와 어디까지가 외부 원장 없이 도는가. 표만으로는 세어지지 않는 것들이다.

㉠ 강제 지점이 일곱이고, 둘씩 ⓪과 ⑤에 몰려 있다. — ★는 하드 차단만 센다. 라운드 상한이 걸린 리뷰 넷(③′·④′·⑤′·⑦)은 판단이 필요해 오탐이 있으므로 ★가 아니다(§5-2). 배선 검증 · 배포물 추적 확인 · 도구 부재 · 이슈 번호 · 쓰기 경계 차단 · 통합 전 차단 · 정합성 판정 기록. 일곱 다 결정적 조건이라 오탐이 원리적으로 없고, 그래서 §5-2의 차단 기준(effective false positive 0%)을 논쟁 없이 만족한다. P7이 실제로 몇 군데에 붙는지가 이 배치에서만 세어진다.

⑤가 둘이 된 것은 이번 판이다(원장 S8) — 이전에는 「계산적 게이트」 하나로 묶여 있었고 쓰기 경계가 실제로 차단이 되는지가 미검증이었다. 실측으로 확정돼 갈라졌다(§5-2 실측 1).

그리고 ⑥의 ★가 사라져 여덟에서 일곱이 됐다(원장 S12). 줄어든 것이 약해진 것이 아니다 — 「전이표 검증 · 직접 편집 금지」는 직접 붙일 수 있는 라벨을 막던 것인데, 상태를 산출물에서 계산하면 만들어야 존재하므로 불가능한 전이가 원리적으로 생기지 않는다. 강제 지점이 줄어드는 가장 좋은 방식은 구조가 그것을 흡수하는 것이다.

가장 이른 강제가 가장 무겁다. 설치가 어긋나면 이후 단계의 게이트가 실패하지 않고 조용히 없어진다 — 나중 단계에서는 검출되지 않는 종류의 고장이다. 실측된 근거가 둘이다 — 핀이 gitignore 안에 있었고(추적되지 않는 핀은 핀이 아니다), 훅 배선이 없으면 조용히 통과한다 — 설정 파일이 상속되지 않아 세션 시작이 가능한 디렉터리마다 설정과 스크립트가 필요하다. L2의 계산적 게이트 전부가 그 배선 위에 선다.

다만 그 디렉터리는 하나다(원장 S10) — 세션을 저장소 루트에서만 시작하고, 워크트리는 커밋이 덮는다. 그래서 이것은 장애물이 아니라 대가가 된다: 루트에서 시작한다는 것이 규약이고 위반이 조용하다(§6-1).
⚠ 2026-08-09 정정 — 이 구분을 「오프라인 ⇄ 온라인」으로 부르던 것이 틀렸다. 하네스가 Claude Code 위에서 도는 이상 에이전트가 코드를 쓰는 것 자체가 네트워크다 — 「⑤는 오프라인에서 돈다」는 성립한 적이 없다(사용자 지적). 추론 리뷰를 커밋 경계에 넣기 전에도 그랬다.

이 구분이 실제로 가르던 것은 「하네스가 의존하는 외부 원장」이다 — GitHub과 원격 DB. fail-closed가 걸린 것도, §7-2의 캐시 규칙이 대상으로 삼는 것도 그 둘이다. 모델 API는 이 설계가 고르는 변수가 아니라 전제이고, 끊기면 하네스 전체가 멈추므로 배치의 문제가 아니다.

그래서 남는 실패 시나리오는 「GitHub이 안 될 때」와 「DB가 안 될 때」다 — 그 둘에 대해서만 fail-open/closed를 정한다. 모델 호출이 부분적으로 실패하는 경우(레이트 리밋 등)는 「미검증」으로 표시한다 — 비차단이라 막지 않지만 조용히 지나가게 두지도 않는다.

㉡ 외부 원장을 요구하는 단계가 셋뿐이다 — ⓪ · ③ · ⑦. ⑥이 빠진 것이 이번 판이다(원장 S12) — 유일한 fail-closed 외부 원장 요구였는데, 상태를 git에서 계산하면서 빠졌다. ①은 요구가 아니다 — 원격 기본값이 없으면 배포물 동봉 사본으로 진행한다. 그리고 ④·⑤·⑧은 로컬로만 뻗는다. 하네스 전체가 외부 원장에 묶이는 것이 아니라 계층 간 신호만 묶인다. 이 비대칭이 §7-2의 캐시 규칙(읽기)과 같은 이유에서 나오고, 차단도 같은 비대칭을 따른다 — task는 커밋이라 외부 원장 없이 돌고, 막히는 것은 계층 간 신호뿐이다(③ 착수의 이슈 조회 · ⑦ 통합).

6-3. story 상태 기계

story 하나가 지나는 상태는 다섯이고 integrated가 종착이다. task는 상태를 갖지 않는다 — 아래 도해의 전이는 전부 story의 것이다.

이 다섯은 어휘이지 저장되는 값이 아니다 — 산출물에서 계산한다(원장 S12). P2를 끝까지 밀면 상태 필드는 기록이 아니라 산출물의 캐시이고, 뒷받침하는 산출물이 전부 영구적이면 캐시가 필요 없다.

상태무엇이 있으면 그 상태인가어디
baseline기준선 결과 객체 커밋이 있다작업 브랜치 (git)
verified모든 task 커밋이 게이트를 통과했다작업 브랜치 (git)
reviewed리뷰 기록 커밋이 있다 — 가드 ㉡의 앵커가 이 SHA다작업 브랜치 (git)
integratedPR이 머지됐다 (= 이슈가 닫혔다)GitHub
blocked계산되지 않는다 — 막힌 사유는 사람이 쓴다이슈 라벨 + 코멘트

계산 재료가 integrated 하나를 빼고 전부 git이라 외부 원장 없이 답이 나온다 — 그래서 ⑥이 외부 원장을 요구하는 단계에서 빠졌다.

그리고 강제 지점이 하나 줄었다. 라벨은 직접 붙일 수 있어 permissions.deny가 필요했는데, 산출물은 만들어야 존재하므로 불가능한 전이가 원리적으로 생기지 않는다. 강제를 뺀 것이 아니라 구조가 흡수한 것이다.

남는 한정어 — 산출물도 위조할 수 있다. 기준선 결과 객체 커밋을 직접 쓸 수 있다. 라벨을 직접 붙이는 것과 같은 수준이고, 다만 내용이 스키마로 검증 가능하다는 점이 낫다. 완전한 방어가 아니다.

P2가 상태의 자격을 정한다 — 전이를 정당화하는 산출물이 있어야 상태다. 그래서 모든 간선에 행위자가 아니라 산출물이 적혀 있다. sub task는 이 그림에 없다 — 체크리스트이지 상태가 아니다(§4-8).

상태 기계는 story 하나다 — task는 상태를 갖지 않는다. 아래 도해의 다섯 상태는 story의 것이고, task가 도는 기준선 기록 → 기대 방향 확인 → 커밋은 상태 기계가 아니라 판정 절차다. 산출물은 있지만 전이표가 없고, 진행은 계획 문서 체크박스가 기록한다(§4-8).

어휘가 task에서 올라왔기 때문에 헷갈리기 쉽다. baseline·verified는 §5-1의 판정 형태에서 온 이름인데, story 수준에서는 “첫 task가 기준선을 기록했다” · “모든 task가 게이트를 통과했다”를 뜻한다.

가르는 근거 셋. ① integrated를 “커밋됨”으로 두면 §5-4의 “story 경계에서는 예외 없음 — PR은 반드시 verified”와 어긋난다 — 상태가 되돌아간다. ② reviewed는 브랜치 전체를 대상으로 하므로 커밋 단위에 붙을 수 없다(§5-2 검토 4번). ⚠ 2026-08-09 정정 — 이 근거는 원래 “§5-2에서 통합 후로 확정됐으므로”라고 적었다. S4가 reviewed를 통합 전으로 되돌린 뒤에도 남아 있었고, §1-2와 정면으로 어긋났다(원장 S4). 결론은 그대로이고 이유가 바뀐다. ③ 원 출처가 참고 하네스의 토픽 상태 기계이고, 토픽 = 지금의 story다.

도해가 이 절에 있는 것은 어휘의 출처가 §5-1이기 때문이다 — baseline·verified가 어디서 왔는지를 읽은 뒤라야 그림이 읽힌다. 대상은 §4-3의 story다.
