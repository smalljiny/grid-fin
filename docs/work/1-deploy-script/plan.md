# 구현 계획 — 이슈 #1 배포 스크립트

## 이 문서가 하는 일

**스펙이 정한 것을 커밋 단위로 쪼갠다.** 무엇을 만들지는 [스펙](spec.md)이 정했고, 여기서는 **어떤 순서로 만들고 각 커밋이 무엇으로 끝났다고 판정하는가**만 정한다.

**여기서 새 결정을 하지 않는다.** 쪼개다 「이건 안 정해졌네」가 나오면 §5에 적고 스펙으로 돌려보낸다.

## 1. 쪼갠 기준

**검증 조건 C1~C21을 누가 통과시키는가로 갈랐다.** 각 task는 **자기 조건을 통과시키고 앞 task의 조건을 깨지 않는다.**

**순서를 정한 것은 의존이다** — fixture가 없으면 어떤 시험도 돌지 않고, 매니페스트가 없으면 병합의 base를 못 찾는다.

## 2. task 6개

### T1 — fixture와 준비물 · `config`

**무엇**: `payload/`에 자리표시본을 넣고 `tests/make-fixtures.sh`를 만든다.

- `bin/gridfin` — uv 기반 Python. **뼈대만.** deploy 는 T2가 채운다
- `payload/claude/settings.json` — `hooks`(SessionStart·PreToolUse) · `permissions.allow` · `statusLine`
- `payload/claude/scripts/hooks/{session-start,pre-commit,format}.py` — **각 3줄, 파일마다 자기 이름을 담는다**
- `tests/make-fixtures.sh` — 하네스 저장소 8개(V1·V2·V3·RM·CONF·CONFJ·V_SPACE·V_ROOT)를 만들고 경로를 내보낸다
- `docs/tmp/impl-later/verify-deploy.sh` → **`tests/verify-deploy.sh`로 옮긴다**

**`payload/root/`는 만들지 않는다.** #3이 선언 설정 파일을 넣을 때 생긴다.

**완료 조건**: `eval "$(bash tests/make-fixtures.sh)"` 후 8개 경로가 전부 존재하고 각각 git 저장소이며 커밋이 있다. 훅 스크립트 3개의 내용이 서로 다르다.

**T1만 `C` 조건을 갖지 않는다.** 배포 동작을 만들지 않으므로 검사할 조건이 없다. **대신 나머지 다섯 task가 전부 T1의 준비물 위에서 돌므로, T1이 틀리면 뒤가 전부 틀린다.**

**커밋**: `배포 검증에 쓸 fixture와 하네스 저장소 8개를 만든다`

### T2 — 배포·매니페스트·종료 코드 · `infra`

**무엇**: `payload/`를 읽어 대상에 쓰고 매니페스트를 만든다. **병합은 아직 없다** — 빈 대상에 처음 넣는 경로만.

- `payload/claude/` → `.claude/`, `payload/root/` → 루트 매핑
- 매니페스트 필드 7개 기록
- `--from` 인자. **생략하면 매니페스트의 `source.path`로 내려가고, 첫 배포에서 생략하면 `no_source`로 거부한다**
- **`source.remote`로 가져오는 것은 만들지 않는다** — 캐시 디렉터리 위치가 미결이고(스펙 §7) **시험 47개 중 그 경로를 때리는 것이 없다.** 지금은 거기까지 내려가면 거부한다. **정해지면 그때 만든다**
- **종료 코드 `0`·`1`·`2`의 뼈대.** 파일별 결과를 모아 마지막에 코드를 낸다

**종료 코드를 여기서 만드는 이유가 있다.** T3의 C6·C8이 부분 실패(`1`)를, T5의 C11이 전체 거부(`2`)를 **검증 조건으로 요구한다.** 코드를 마지막에 만들면 **T3과 T5가 자기 조건을 통과시킬 수 없다.**

**완료 조건**: **C1 · C2 · C3 · C21**

**커밋**: `payload를 대상에 배포하고 매니페스트를 기록한다`

### T3 — 병합 · `infra`

**무엇**: 두 형식의 3-way merge. base를 하네스 저장소에서 꺼낸다.

- 텍스트 — `git merge-file`, 종료 코드 255와 충돌 구별
- JSON — `owned` 포인터, 식별자 쌍, 판정 3줄
- 충돌 시 `.merged`

**완료 조건**: **C4 · C5 · C6 · C7 · C8 · C14 · C17 · C18 · C19** — C14 는 쓰는 쪽까지다. **지우는 쪽은 T4 가 넓혔다.**

**C14(심볼릭 링크)를 T5에서 당겨 왔다.** T2는 이미 있는 파일을 전부 건너뛰어 링크를 따라갈 일이 없었는데, **T3이 병합을 넣으면서 그 경로가 생겼다.** 위험을 만든 쪽이 막는다.

**C11의 두 갈래도 여기서 함께 선다** — 식별자 유일성 위반과 `sourceHash` 불일치다. **병합을 하려면 그 둘을 먼저 판정해야 하므로 떼어 둘 수 없다.** 나머지(하네스 dirty · 대상이 git 저장소가 아님 · 잠금)는 T5에 남는다.

**커밋**: `텍스트와 JSON을 3-way merge로 갱신한다`

### T4 — 삭제와 부분 상태 · `infra`

**무엇**: 사라진 배포물 처리와 파일별 리비전 유지.

- 이전 매니페스트에 있고 새 payload에 없는 `dest`
- 건너뛴 파일의 `sourceSha`·`sourceHash`·`installedHash` 유지

**완료 조건**: **C9 · C10**

**C9는 T3이 이미 통과시켰다.** 건너뛴 파일에 이전 매니페스트 항목을 붙여 두었기 때문이다. T4가 시작할 때 시험 7·15가 통과하고 있었다.

**C14를 대상 경계까지 넓혔다.** 배포 경로의 `dest`는 `git ls-tree`가 만들어 대상 밖을 못 가리키는데 **삭제 경로는 매니페스트에서 곧장 받는다.** `../victim.txt`와 절대 경로가 저장소 밖 파일을 지웠다(실측). **지우는 경로를 만든 쪽이 막는다** — C14를 T3으로 당겨 온 것과 같은 이유다.

**시험을 5개 더했다**(36·37·38·39·40). 구현을 일부러 틀리게 고쳐 재 보니 **기존 시험 8·21·25가 세 가지를 못 잡았다** — 삭제 판정을 `installedHash` 대신 `sourceHash`로 하는 것, 이미 없는 파일의 항목을 안 빼는 것, 삭제 경로의 링크 방어를 빼는 것. 스펙 §6이 「시험을 더하면 닫힌다」고 꼽아 둔 자리다. **40은 C17이 성공 경로만 재고 있던 것을 넓힌다** — 충돌이나 삭제 보류가 남은 대상이 배포할 때마다 매니페스트를 다시 쓰고 있었고, T3부터 그랬으므로 T4가 깬 것은 아니다.

**커밋**: `사라진 배포물을 조건부로 지우고 건너뛴 파일의 리비전을 유지한다`

### T5 — 저장소 접점 · `infra`

**무엇**: 안전 조건 전부.

- git 저장소 판정 — `rev-parse --is-inside-work-tree`
- 무시 목록 — `--git-common-dir`, 관리 블록, 주입한 것만
- 심볼릭 링크 거부(쓰기), 실행 비트 보존, 파일 이름
- 잠금 `.harness/deploy.lock`
- dirty 판정 — `payload/` 범위

**완료 조건**: **C11의 나머지 · C12 · C13 · C15 · C16**

**C12·C15·C16은 T5가 시작할 때 이미 통과하고 있었다.** 대상 JSON이 무효일 때 안 건드리는 것(시험 16)과 실행 비트 보존(30)과 파일 이름(32)은 T2·T3이 지나가면서 만족시켰다. **T5가 새로 만든 것은 거부 조건 3개와 무시 목록과 잠금이다.**

**시험 도구의 결함을 함께 고쳤다.** 이 머신의 `mktemp -d`가 `TMPDIR`을 안 따라 시험 디렉터리가 정리 범위 밖에 쌓였고, 28의 상대 경로 `../wt`가 실행마다 같은 자리를 가리켜 **옛 워크트리를 재사용했다.** 그 탓에 워크트리 배포를 깨는 변이가 통과했다.

**시험을 5개 더했고**(41·42·43·44·45) **31의 조건을 바꿨다.** 겹쳐 돌리기만으로는 잠금을 재지 못한다 — 같은 변이가 단독 실행과 전체 실행에서 다르게 판정됐다.

**죽은 잠금의 복구는 미결로 보냈다**(미결 목록 Q42). `SIGKILL`이나 전원 차단으로 남은 잠금은 사람이 지울 때까지 그 대상의 배포를 막는다. **아무것도 막지 않으므로 #1을 닫기 전에 정하면 된다.**

**커밋**: `저장소 접점의 안전 조건을 건다`

## 3. 순서와 의존

```
T1 fixture ──▶ T2 배포·매니페스트·종료코드 ──▶ T3 병합 ──▶ T4 삭제·부분상태
                                                 │              │
                                                 └─▶ T5 접점 ◀──┘
                                                         │
                                                         ▼
                                                    T6 --json
```

**T5는 T3 뒤여야 한다.** 병합과 독립으로 보이지만 **C12(무효 JSON)와 C15(병합 뒤 실행 비트)가 병합 경로를 지난다.** 병합이 없으면 그 둘이 실제로 시험되지 않는다.

**T6이 마지막인 이유는 전체 조건을 함께 통과시켜야 하기 때문이다.**

## 4. task를 어떻게 실행하는가

**기존 하네스의 `flow-impl`에서 규율만 차용했다.** 오케스트레이션은 `dev-context.json`에 매여 있어 못 쓰지만 **안의 규율 대부분은 상태 저장과 무관하다.** 판정과 근거는 미결 목록에 남겼다.

**M1은 명령을 직접 치므로 아래는 사람이 따르는 절차다.** M2에서 스킬로 굳을 때 그대로 옮긴다.

| # | 규율 | 왜 |
|---|---|---|
| 1 | **한 번에 한 task.** 착수 전에 무엇을 할지 브리핑하고 승인을 받는다 | 되돌림이 커밋 하나로 끝난다 |
| 2 | **`infra` 종류이거나 완료 조건이 5개 이상이면 착수 브리핑 직후 `advisor`를 부른다** | T2·T3·T5가 해당한다. **설계 위험을 쓰기 전에 본다** |
| 3 | **시작할 때 그 task의 조건이 실제로 실패하는지 먼저 확인한다** | 통과하고 있으면 **시험이 그 규칙을 안 때리는 것**이다. 교차 검토에서 반복해 나온 형태다 |
| 4 | **구현 직후 코드 검토를 받는다** | 설계의 ⑤ 커밋 경계 검토다. 지금은 수동 |
| 5 | **완료 조건을 하나씩 점검하고 통과한 것만 표시한다. PASS·FAIL의 근거를 함께 낸다** | 「C4·C5 통과」만 적으면 **무엇을 근거로 통과했는지 남지 않는다** |
| 6 | **미체크가 남으면 「보고 누락인가 실제 미수행인가」를 묻는다** | 조용한 누락을 막는다 |
| 7 | **커밋 메시지는 이 문서에서 가져온다. 지어내지 않는다.** 검토 지적을 고칠 때는 `amend`하지 않고 새 커밋을 만든다 | 계획의 커밋 메시지가 불변으로 유지되고 **검토 지적의 추적성이 생긴다** |

**`wf-tdd`의 철칙 한 줄도 가져온다** — *실패를 확인하지 않은 테스트는 없는 테스트와 같다.* 다만 **RED 단계는 이미 끝나 있다.** 시험 47개가 있고 `gridfin`이 없어 전부 실패한다. 그래서 3번 규율이 그 자리를 대신한다.

## 5. 각 task가 끝났다고 판정하는 법

**`tests/verify-deploy.sh`의 해당 시험만 돌린다.** T1이 그 파일을 제자리에 놓는다.

**앞 task의 조건이 깨지지 않았는지도 본다** — 회귀를 커밋 단위에서 잡는다. T6에서만 전체를 돌리면 어느 커밋이 깼는지 못 찾는다.

## 6. 쪼개다 나온 것 — 정해졌다

계획을 쓰면서 스펙이 답을 안 주는 곳 넷이 나왔고 **넷 다 T1~T2를 막고 있었다.** 2026-08-19에 정했고 스펙에 반영했다.

| 무엇 | 결정 | 왜 그쪽인가 · 대가 |
|---|---|---|
| 검증 스크립트의 자리 | **`tests/`** — `make-fixtures.sh`와 `verify-deploy.sh` 둘 다 | 배포물이 아니고 구현이 사는 동안 계속 돌아야 한다. **소멸 문서와 함께 지우면 고칠 때마다 다시 만들어야 한다.** 산출물이 4종에서 5종이 됐다 |
| `--from` 생략 | **매니페스트의 `source.path` → `source.remote` 순으로 찾는다.** 첫 배포에서 생략하면 `no_source`로 거부 | **이미 정한 조회 순서와 그대로 이어진다** — `--from`이 없으면 2번부터 시작할 뿐이다. 대가: 첫 배포와 재배포의 인자가 달라 보인다 |
| `payload/root/`가 빌 때 | **만들지 않는다.** 매핑이 존재하는 하위 디렉터리를 순회한다 | git이 빈 디렉터리를 추적하지 않아 **자리를 잡아 두려면 배포하면 안 되는 파일을 넣게 되고 제외 규칙이 하나 는다.** 대가: #3 전까지 그 자리가 안 보인다 |
| 자리표시본 내용 | **파일마다 자기 이름을 담는 3줄** | 내용이 같으면 `sourceHash`가 셋 다 같아져 **파일을 뒤바꿔 쓰는 구현이 해시 비교를 통과한다.** 3줄인 것은 검증이 2번째 줄에 사용자 줄을 넣기 때문이다 |

**막힌 것이 남아 있지 않다.** T1부터 시작할 수 있다.
