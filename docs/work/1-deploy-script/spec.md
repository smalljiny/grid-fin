# 배포 스크립트 — 이슈 #1 작업 스펙

## 1. 개요

### 1.1 배경

**기존 하네스의 배포는 고장나 있었고, 고장의 형태가 측정되어 있다**([배포 방식 조사](../../research/harness-distribution.md), 1차 실측).

- **핀이 무시 목록 안에 있었다.** `deploy-harness.sh`가 심는 ignore 블록이 매니페스트 자신을 포함했다. **추적되지 않는 핀은 버전 식별 기능을 하지 못한다**(§1.1).
- **통짜 무시가 관리 블록을 덮었다**(§1.2).
- **`.gitignore` 통짜 무시 아래에서는 갱신이 로컬 수정을 경고 없이 삭제했다**(§4.2 실증).

**세 가지가 같은 뿌리에서 나온다** — 배포물이 어느 버전인지 기록되지 않았고, 갱신이 사용자 수정을 지켰는지 확인할 방법이 없었다.

### 1.2 목적

**하네스를 대상 프로젝트에 넣고, 다시 넣어도 사용자가 고친 것을 지우지 않는다.** 그리고 **어느 버전이 들어가 있는지 언제든 확인할 수 있다.**

## 2. 목표

무엇이 참이 되면 이 이슈가 끝나는가.

1. **하네스 저장소의 파일이 대상 프로젝트에 설치된다** — 대상이 워크트리여도, 파일 이름에 공백이나 유니코드가 있어도.
2. **어느 리비전이 설치됐는지 매니페스트가 기록하고, 그 리비전에서 설치 당시의 내용을 다시 꺼낼 수 있다.**
3. **다시 실행하면 사용자가 고친 부분이 살아남고 하네스의 갱신분이 반영된다.** 양쪽이 같은 자리를 다르게 고친 경우에는 **살아 있는 파일을 건드리지 않는다.**
4. **안전하게 진행할 수 없는 상황에서는 아무것도 쓰지 않거나 그 파일만 건너뛰고, 부르는 쪽이 무엇이 됐고 무엇이 안 됐는지 알 수 있다.**

## 3. 구조

### 3.1 소스와 목적지

소스는 `payload/`에 두고 배포 스크립트가 읽어 대상에 쓴다. `.claude/`는 설치되는 곳이지 소스가 아니다.

```
payload/
  claude/   → 대상 저장소의 .claude/
  root/     → 대상 저장소 루트 (#3부터 생긴다)
```

**매핑은 존재하는 하위 디렉터리를 순회한다.** `payload/root/`는 #3이 선언 설정 파일을 넣을 때 생기고, **그전까지는 만들지 않는다** — git이 빈 디렉터리를 추적하지 않으므로 자리를 잡아 두려면 배포하면 안 되는 파일을 넣게 되고, 그러면 제외 규칙이 하나 는다.

**소스 디렉터리 안에서는 목적지 이름에 점을 붙이지 않는다.** 이 저장소의 `.gitignore` 3번째 줄 `.claude/`에 앵커가 없어 하위 경로의 같은 이름까지 잡는다(1차 실측 2026-08-19). 점을 붙이면 소스가 커밋되지 않고, **추적되지 않는 소스는 배경 §1.1이 관측한 상태와 같아진다.**

### 3.2 배포 대상

설계 §7-4가 정한 8가지 중 **M0에서 넣는 것은 5개**다.

| 무엇 | M0에서 넣나 | 내용을 채우는 이슈 |
|---|---|---|
| 훅 스크립트 4개 | 예 | #2 |
| `settings.json` — 훅 선언 | 예 | #2 |
| `settings.json` — 권한 허용 | 예 | #2 |
| 선언 설정 | 예 | #3 |
| 매니페스트 | 예 | 이 이슈 |
| 명령 스킬 · 검토용 서브에이전트 | 아니오 | M2 |
| 상태 표시줄 · 코딩 규약 · 기술 스택 지식 | 미정 | — |

**배포 대상이 늘어도 배포 스크립트는 고치지 않는다.** 배포물 확인이 매니페스트의 `files` 배열과 대조하므로 목록이 자라면 대조 대상만 자란다.

### 3.3 갱신 규칙 — 두 형식 모두 3-way merge

**세 입력은 형식과 무관하게 같다.**

| 입력 | 무엇 |
|---|---|
| base | 이전 배포 시점의 payload 내용. **하네스 저장소**에서 `git show <그 파일의 sourceSha>:<src>`로 꺼낸다 |
| ours | 대상에 지금 있는 파일 |
| theirs | 이번에 배포할 payload 내용 |

**base가 대상이 아니라 하네스 저장소에서 나오는 것이 이 설계의 핵심이다.** 배포물을 추적하지 않으므로(S26) 대상에는 이전 버전이 없다.

| 형식 | 알고리즘 |
|---|---|
| 텍스트 | `git merge-file`. 줄 단위 |
| JSON | 구조 단위. `owned`가 가리키는 자리만 |

**판정은 세 줄이고 부재도 값으로 센다.**

1. ours가 base와 같으면 **theirs를 따른다.** theirs가 부재면 삭제다.
2. theirs가 base와 같으면 **ours를 따른다.**
3. 둘 다 base와 다르면 값이 서로 같을 때만 그대로 두고, 다르면 **충돌**이다.

**`pointer`가 가리키는 자리가 없는 것과 값이 JSON `null`인 것은 다르다.** 부재는 위 규칙에서 「부재」로, `null`은 값 `null`로 센다. **둘을 같게 다루면 사용자가 지운 것과 `null`로 둔 것이 구별되지 않는다.**

**경우를 나열하지 않는 이유가 있다.** 나열하면 빠뜨린다 — 양쪽이 같은 값으로 수렴한 경우, 양쪽이 같은 원소를 지운 경우, 사용자가 지웠는데 하네스가 고친 경우가 그런 것들이다.

### 3.4 base를 어느 저장소에서 꺼내는가

`gridfin deploy`는 대상 프로젝트에서 실행되므로 하네스 저장소의 위치가 계약에 있어야 한다. **순서대로 찾는다.**

1. `--from <경로>` 인자
2. 매니페스트의 `source.path`
3. 매니페스트의 `source.remote`를 캐시 디렉터리로 fetch

**`--from`을 생략하면 2번부터 시작한다.** 재배포는 매니페스트가 출처를 알고 있으므로 인자가 필요 없다. **첫 배포에는 매니페스트가 없으므로 거기서만 필수이고, 생략하면 `no_source`로 전체 거부한다.**

**`--from`은 이번에 배포할 payload의 출처이고, base는 그 파일의 `sourceSha`를 가진 저장소 어디서든 꺼낸다.** 둘이 같은 저장소일 필요가 없다. 실무에서는 같은 저장소의 다른 리비전이라 `--from` 하나로 끝난다.

**되돌림은 정상 경로다.** `sourceSha`가 이전 리비전보다 뒤로 가도 된다. base는 *이전에 쓴 리비전*이고 theirs는 *이번 리비전*일 뿐 순서 관계를 요구하지 않는다.

**한 번 배포한 리비전이 하네스 저장소에서 사라지면 안 된다.** 얕은 클론과 이력 재작성이 그것을 깬다. 깨지면 그 파일은 병합되지 않고 건너뛰어진다 — **조용히 덮이지는 않는다.**

### 3.5 JSON 소유 계약

**`merge`와 `owned`는 `payload/rules.json`이 선언한다.** payload 안의 경로를 키로 삼는다. **적지 않은 파일은 `text`로 다루고, `json`은 반드시 선언해야 한다.**

**이 파일은 배포되지 않는다.** 매핑이 하위 디렉터리만 순회하므로 payload 최상위의 파일에는 목적지가 없다. **제외 규칙을 따로 만들지 않아도 된다.**

**`gridfin` 안에 박지 않는 이유가 있다.** 배포 대상이 늘어도 배포 스크립트를 고치지 않는다는 것이 §3.2의 요구인데, 코드에 박으면 M2에서 스킬과 서브에이전트가 들어올 때마다 고쳐야 한다.

`owned`의 각 항목이 자리 하나와 그 자리의 식별자를 지정한다. **`pointer`가 배열을 가리키면 원소마다, 그 밖이면 값 자체에** 판정을 적용한다.

**식별자는 필드 하나가 아니라 원소 안의 JSON Pointer 목록이고 값들의 쌍이다.** 실물에서 **어느 한 필드도 단독으로는 유일하지 않다**(1차 실측 2026-08-19, 기존 하네스 `.claude/settings.json`).

| 사건 | 원소 | `/matcher` 고유 | `/hooks/0/command` 고유 | 쌍 |
|---|---|---|---|---|
| `PostToolUse` | 3 | **2** | 3 | 3 |
| `PreToolUse` | 3 | 3 | **2** | 3 |
| `Stop` | 2 | **1** | 2 | 2 |

`matcher`는 `PostToolUse`에서 겹치고 `SessionStart`·`Stop`에는 필드가 없다. `command`는 `PreToolUse`에서 겹친다 — 같은 스크립트를 `Edit`과 `Write` 두 matcher에 등록해 두었다.

**원시 배열에서는 충돌이 생기지 않는다.** 원소가 곧 식별자라 수정이 삭제와 추가로 보인다. 허용 목록에서는 그것이 맞는 결과다.

**식별자가 배열 안에서 유일하지 않으면 배포를 거부한다.** 짝짓지 못한 채 병합하면 어느 쪽이 사용자 것인지 모르는 상태로 덮어쓴다.

### 3.6 매니페스트 계약

`.harness/manifest.json`에 쓴다.

| 필드 | 자리 | 답하는 질문 |
|---|---|---|
| `src` | 파일별 | payload 안의 경로. **base를 꺼낼 때 `git show <sourceSha>:<src>`로 쓴다** |
| `dest` | 파일별 | 대상 안의 경로. **배포물 확인이 대조하는 목록이다** |
| `attemptedSha` | 최상위 | 이번 배포가 목표한 리비전. **기록용이고 base 복원에 쓰지 않는다** |
| `deployedAt` | 최상위 | 언제 배포했나. 기록용 |
| `source.remote` · `source.path` | 최상위 | 어느 저장소에서 꺼내는가. **원격이 없는 저장소에서는 `source.remote`가 빈 문자열이다** |
| `sourceSha` | 파일별 | **이 파일의 base를 어느 리비전에서 꺼내는가** |
| `sourceHash` | 파일별 | 꺼낸 base가 그때 배포한 그것이 맞는가 |
| `installedHash` | 파일별 | 설치 이후 사용자가 바꿨는가 |
| `merge` | 파일별 | 줄 단위인가 구조 단위인가 |
| `owned` | 파일별 | 하네스가 소유한 자리와 원소 식별자 |

**`sourceHash`와 `installedHash`는 대체 관계가 아니다.** 사용자 수정을 보존해 병합하면 **설치본이 업스트림 원문과 달라진다.** 하나로 합치면 base 검증과 드리프트 검출 중 하나가 반드시 깨진다.

**리비전이 파일별인 이유가 있다.** 충돌한 파일과 base를 못 꺼낸 파일은 **쓰이지 않은 채 이전 버전으로 남는다.** 최상위에 하나뿐이면 그 상태를 적을 수 없고 **다음 배포가 틀린 base로 병합한다.**

**`files`는 `payload/`에서 나온 것만 세고 매니페스트 자신은 넣지 않는다** — 자기 해시를 자기 안에 담을 수 없다. **`files`는 「배포물이 제자리에 있는가」까지만 답한다** — #2의 훅 등록 확인은 `settings.json`의 선언을 파싱해 교차 검사해야 한다.

**릴리스 저장소들은 같은 객체 이력을 공유해야 한다.** 리비전은 파일별인데 그것을 꺼낼 저장소 지정은 하나뿐이다.

### 3.7 저장소 접점

**대상은 git 저장소여야 한다.** 판정은 `git rev-parse --is-inside-work-tree`로 한다 — **워크트리에서 `.git`은 디렉터리가 아니라 파일이라** `test -d`가 틀린다(1차 실측 2026-08-19).

**무시 목록은 저장소당 하나다.** 경로를 `git rev-parse --git-common-dir`로 푼다. **워크트리 전용 exclude는 git이 읽지 않는다**(1차 실측, 두 번 확인). 적용되는 것은 공용 하나뿐이라 **메인과 모든 워크트리에 함께 걸린다** — S26이 적은 「주입한 항목만 등록한다」를 워크트리 단위로 쓸 수 없다.

**심볼릭 링크는 쓰기만 거부한다.** `dest` 경로의 어느 구성 요소라도 링크이면 건너뛰고 보고한다 — 링크를 따라가면 **저장소 밖 파일을 고친다**(1차 실측). **읽기만 하는 검사는 따라간다.**

**같은 대상에 둘이 동시에 배포하지 못하게 막는다.** `.harness/deploy.lock`을 `mkdir`로 잡는다. 잠금이 없으면 **나중에 시작한 배포가 먼저 끝나 옛 배포가 최신을 되돌린다**(1차 실측).

**실행 비트를 보존하고 줄 끝을 정규화하지 않는다.** `dest`에 개행을 허용하지 않는다.

**하네스가 dirty하면 거부한다.** 정의는 `git -C "$HARNESS" status --porcelain -- payload/`가 비어 있지 않은 상태다. **범위를 `payload/`로 좁힌다** — 문서를 고치는 중이라고 배포를 막을 이유가 없다.

### 3.8 실패 범위와 종료 코드

| 범위 | 무엇 | 왜 |
|---|---|---|
| **전체 거부** | 하네스 dirty · 대상이 git 저장소가 아님 · 식별자 유일성 위반 · `sourceHash` 불일치 · 잠금 실패 · 무시 목록을 못 씀 · 대상 루트에 쓸 권한 없음 · **출처를 못 찾음** | **입력이 잘못됐다는 신호**다. 어느 파일도 안전하게 병합할 수 없다 |
| **파일별 건너뛰기** | base 부재 · 충돌 · 대상 JSON 무효 · 사용자가 고친 삭제 대상 · `dest`가 심볼릭 링크 · 그 파일에 쓸 권한 없음 | **그 파일만의 조건**이다 |

**종료 코드는 3개다.** `0` 완전 성공 · `1` 부분 실패 · `2` 전체 거부. **세부 원인은 `--json`이 담는다** — 코드는 「무엇을 해야 하는가」만 가른다.

**사람이 읽는 출력을 계약으로 쓰지 않는다.** 문구를 다듬을 때마다 검증이 깨진다.

```json
{ "outcome": "success | partial | rejected",
  "reason": "harness_dirty | not_a_git_repo | duplicate_identifier | source_hash_mismatch
             | lock_busy | exclude_write_failed | no_permission | no_source",
  "files": [ { "dest": "...", "status": "updated | unchanged | conflict | skipped
                                        | drift | deleted | delete_pending",
               "detail": "...", "merged": "..." } ] }
```

|---|---|---|
| **하네스가 만드는 실행물** | **bash와 uv 기반 Python뿐. Node를 쓰지 않는다** | 원장 S30 — 대상 프로젝트와 의존성이 뒤섞인 경험 |
| **훅 호출** | **셔뱅 `#!/usr/bin/env -S uv run --script` + `settings.json`은 경로만** | 실행 비트 보존(C15)이 몸값을 한다. `env -S` 동작을 실측했다 |
| **`gridfin` 찾기** | **저장소의 `bin/`. `verify-deploy.sh`가 PATH 앞에 붙인다** | 설치 없이 시험이 돈다. 실사용 설치는 나중에 정한다 |
| 소스 디렉터리 이름 | `payload/` | 설계가 쓰는 「배포물」과 대응하고 `src/`와 부딪히지 않는다 |
| 목적지 이름에 점 | **붙이지 않는다** | `.gitignore`의 앵커 없는 `.claude/`가 하위까지 잡는다 (1차 실측) |
| CLI 이름 | `gridfin` | 이슈 #1~#4의 검증 명령이 매여 있다 |
| 갱신 방식 | **두 형식 모두 3-way merge** | 원장 S27 · 배포 방식 조사 §4.2 |
| base 출처 | **하네스 저장소** (대상 아님) | 배포물을 추적하지 않으므로(S26) 대상에 이전 버전이 없다 |
| 병합 판정 | **표준 3-way 3줄, 부재도 값** | 경우를 나열하면 빠뜨린다 (실측: 4가지 누락) |
| JSON 소유 단위 | **배열 원소, 식별자는 포인터 쌍** | 단독 필드는 실물에서 전부 깨진다 (1차 실측) |
| **`merge`·`owned`의 출처** | **`payload/rules.json`** — payload 최상위라 배포되지 않는다 | 코드에 박으면 배포 대상이 늘 때마다 고쳐야 한다 |
| 매니페스트 필드 | **최상위 3개**(`attemptedSha`·`deployedAt`·`source`) + **파일별 6개**(`src`·`dest`·`merge`·`sourceSha`·`sourceHash`·`installedHash`), 그리고 **`merge`가 `json`일 때만 `owned`** | 원장 S27 정정. **텍스트 파일에 빈 `owned`를 채우지 않는다** — 뜻이 없는 값이다 |
| 리비전 위치 | **파일별** | 부분 상태를 표현하지 못하면 다음 배포가 틀린 base를 쓴다 |
| 실패 범위 | **전체 거부 / 파일별 건너뛰기 2종** | 조건이 입력의 문제인가 그 파일의 문제인가 |
| 종료 코드 | **3개 + `--json`** | 종류마다 코드를 두면 늘 때마다 부르는 쪽이 표를 따라다닌다 |
| 심볼릭 링크 | **쓰기만 거부, 읽기는 따라감** | 링크가 저장소 밖을 고치는 것이 관측됐다 |
| 동시 실행 | **`.harness/deploy.lock`** | 잠금 없이 옛 배포가 최신을 되돌리는 것이 관측됐다 |
| 무시 목록 | **저장소 공용 exclude 한 블록** | 워크트리 전용 exclude를 git이 읽지 않는다 (1차 실측) |
| dirty 범위 | **`payload/` 안만** | 문서 수정이 배포를 막을 이유가 없다 |
| 멱등성 | **바뀐 것이 없으면 매니페스트를 다시 쓰지 않는다** | `deployedAt` 때문에 해시가 흔들리면 배포물 확인이 「바뀌었다」와 「다시 배포했다」를 구별 못 한다 |
| 되돌림 | **정상 경로** | base는 이전에 쓴 리비전일 뿐 순서 관계를 요구하지 않는다 |
| fixture payload | **#1이 자리표시본을 만든다** | 배포 스크립트를 혼자 검증하려면 배포할 것이 있어야 한다 (사용자 결정) |

**근거의 전문은 [미결 사항 원장](../../draft/open-questions.md)의 S26·S27·S28에 있다.** 이 표는 항목과 결정만 센다.

## 5. 범위 밖

| 무엇 | 어디서 |
|---|---|
| 훅 스크립트의 **내용**, `settings.json`의 훅 선언·권한 허용 **내용** | #2 |
| 워크트리 주입 스크립트 | #2 |
| 선언 설정 파일의 이름과 필드 | #3 |
| 명령 스킬, 검토용 서브에이전트 | M2 |
| 상태 표시줄·코딩 규약·기술 스택 지식을 배포할지 | 설계에서 아직 안 정했다 |
| 평가 세트 배포 | 배포 대상이 아니다 — 스킬 파일 안에 조건을 선언한다 |

**이 이슈가 만드는 것은 산출물 5종이다.**

| 무엇 | 어디 |
|---|---|
| 배포 스크립트 | `bin/gridfin` — **uv 기반 Python** |
| 매니페스트 | 대상의 `.harness/manifest.json` |
| fixture payload | `payload/` |
| 하네스 저장소 8개를 만드는 스크립트 | `tests/make-fixtures.sh` |
| 검증 시험 | `tests/verify-deploy.sh` |

**검증 스크립트는 배포물이 아니다.** 배포 대상 목록에 없고 대상 프로젝트로 나가지 않는다. **구현이 살아 있는 동안 계속 돌아야 하므로 소멸 문서와 함께 지우지 않는다.**

**fixture가 이 모양이어야 하는 이유가 있다.** 갱신·삭제·충돌 경로를 전부 밟으려면 **지울 파일**(`format.py`)과 **하네스가 뺄 배열 원소**(`permissions.allow`의 항목 하나)와 **`matcher`가 있는 사건과 없는 사건**(`PreToolUse`·`SessionStart`)과 **값 자리**(`statusLine`)를 다 가져야 한다. **검증 준비물 V1이 곧 이 자리표시본이다.**

```json
{ "hooks": {
    "SessionStart": [ { "hooks": [ { "type": "command", "command": ".../session-start.py" } ] } ],
    "PreToolUse":   [ { "matcher": "Write",
                        "hooks": [ { "type": "command", "command": ".../pre-commit.py" } ] } ] },
  "permissions": { "allow": ["Bash(git:*)", "Bash(gh:*)"] },
  "statusLine": { "type": "command", "command": ".../status.py" } }
```

**자리표시본 훅 스크립트는 파일마다 자기 이름을 담는다.**

```python
#!/usr/bin/env -S uv run --script
# /// script
# requires-python = ">=3.11"
# ///
"""#2가 채운다 — 지금은 자리표시본. hook: session-start"""
import sys

sys.exit(0)
```

**내용이 같으면 `sourceHash`가 셋 다 같아져 파일을 뒤바꿔 쓰는 구현이 해시 비교를 통과한다.** 가르는 비용이 한 줄이다. 3줄인 것도 이유가 있다 — **검증이 2번째 줄에 사용자 줄을 넣어 3-way merge를 시험한다.**

**fixture는 시험용 최소 배포물이고 M0의 최종 배포 목록이 아니다.** `statusLine`이 fixture에 있는 것도 **값 자리를 시험하기 위해서이지 배포하기로 정해서가 아니다.**

**시험마다 「배포가 실제로 멈췄는가」를 함께 본다.** 출력 메시지만 보면 *메시지는 냈는데 배포는 진행된* 구현이 통과한다.

**이 검증이 재지 않는 것 넷.**

1. **매니페스트를 마지막에 한 번만 쓰는지** — 파일별로 쓰는 구현과 최종 상태가 같아 쓰기 횟수를 세거나 중간에 죽이는 장치가 있어야 구별된다.
2. **전체 거부 조건 3개** — 무시 목록을 못 씀 · 대상 루트에 쓸 권한 없음 · 출처를 못 찾음. **§3.8이 전체 거부로 정했는데 시험이 없다.**
3. **건너뛰기 3가지의 매니페스트 보존** — C9가 보는 것은 base 부재(7)와 JSON 충돌(15)이고, 8이 사용자가 고친 삭제 대상을 더한다. **텍스트 충돌 · 무효 JSON · 심볼릭 링크**는 파일만 보고 매니페스트 항목은 보지 않는다.
4. **연쇄 갱신에서 파일별 리비전이 매번 올라가는지** — 23번이 파일 내용은 보지만 `sourceSha`의 이동은 보지 않는다.

**2·3·4는 시험을 더하면 닫힌다. 1은 관측 수단이 있어야 한다.** 구현 단계에서 시험을 더할 때 여기부터 본다.

> **보강 2026-08-19 · T4 구현.** 시험 4개를 더했다(36·37·38·39). 구현을 일부러 틀리게 고쳐 어느 시험이 잡는지 재 보니 **세 가지가 아무 시험에도 안 걸렸다** — ① 삭제 판정을 `installedHash` 대신 `sourceHash`로 해도 통과했다(삭제 대상 `format.py`가 한 번도 병합되지 않아 두 값이 같았다) ② 이미 없는 파일의 항목을 안 빼도 통과했다 ③ 삭제 경로의 심볼릭 링크 방어를 빼도 통과했다.
>
> **그리고 지우는 쪽에만 있는 구멍을 하나 찾았다.** 배포 경로의 `dest`는 `git ls-tree`가 만들어 대상 밖을 못 가리키지만, **삭제 경로는 매니페스트에서 곧장 받는다.** `../victim.txt`와 절대 경로를 매니페스트에 넣으면 **저장소 밖 파일이 지워지고 종료 코드가 0이었다**(실측). C14를 그 경계까지 넓혔다.

## 7. 미결

이 이슈를 막지는 않는다.

| 무엇 | 언제 |
|---|---|
| 선언 설정 파일의 이름과 필드 | #3 |
| 상태 표시줄에 무엇을 표시할지 | 미정 |
| 코딩 규약·기술 스택 지식을 배포할지 | 미정 |
| 스킬이 여럿일 때의 로딩 규칙 | M2 |
| `source.remote`를 fetch할 캐시 디렉터리 위치 | 첫 실행에서 그 경로를 실제로 쓸 때 |

전부 **배포 대상 목록에만 항목을 더하는 변경**이고 매니페스트 스키마를 고치지 않는다.

## 8. 왜 이것이 먼저인가

배포가 되어야 훅을 설정에 등록할 수 있고, 훅이 등록되어야 이후 작업을 강제할 수 있다. **M0의 나머지 세 작업이 전부 배포 위에서 진행된다.**
