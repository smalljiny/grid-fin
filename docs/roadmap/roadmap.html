grid fin 구현 로드맵

조사와 설계는 끝났고, 구현이 시작됐습니다. M0의 네 가지 중 배포 스크립트가 끝났습니다(bin/gridfin, PR #15, 2026-08-20 머지). 남은 세 가지는 훅 스크립트, 선언 설정 파일, Python 검사 어댑터입니다. 넷이 모두 끝나면 grid fin 저장소에 배포하고, 그 뒤부터는 하네스가 자기 개발 과정에도 적용됩니다.

현재 기준선 — 조사 31편, 설계 드래프트 5편, 해소한 미결 53건, 남은 미결 23건입니다(미결 목록 파일의 항목 수). 이 문서는 일정표가 아니라 실행 순서를 정리한 로드맵입니다. 개인 프로젝트 규모에서는 통계적으로 설계를 검증하기 어렵기 때문에(평가 조사 §1.5), 실제 검증은 워크플로를 처음부터 끝까지 한 번 실행하는 M1에서 시작합니다.

M0에서 만든 산출물을 grid fin 저장소에 배포합니다. 이 관문을 지나면 이후 작업은 모두 게이트를 통과해야 합니다. 스킬은 아직 없어도 됩니다. 실제로 강제하는 것은 훅과 설정이고, 스킬은 절차를 안내하는 역할입니다.

훅 등록 확인 — 훅 네 개가 설정에 등록됐는가 매니페스트가 제자리에 있는가 — 무엇을 배포했는지 기록됐는가 쓰기 경계와 커밋 경계가 실제로 막는가

배포물 확인은 CP1에서 실행하지 않습니다. 아직 작업 워크트리가 없어서 대조할 대상이 없기 때문입니다. 검사는 M0에서 만들고, 처음 실행하는 시점은 M1에서 첫 워크트리를 만들 때입니다.

그때의 대조 기준은 매니페스트입니다. 배포 스크립트가 설치한 항목을 매니페스트에 기록하고, 이후 검사는 그 목록과 실제 워크트리를 비교합니다. 고정 목록을 문서에 따로 두지 않는 이유는 배포 단위가 늘 때마다 여러 문서를 함께 고쳐야 하는 일을 피하기 위해서입니다. 스킬이 0개면 0개로 일치하고, M2에서 스킬이 늘어도 같은 검사를 그대로 사용할 수 있습니다.

CP1을 먼저 두는 이유 — 참고 하네스에서는 설정 파일이 워크트리에 따라가지 않아 게이트가 통째로 사라진 적이 있습니다. 이번에는 grid fin 저장소에 먼저 적용해 보고, 배포 전 백업을 남겨 되돌릴 수 있게 합니다.
